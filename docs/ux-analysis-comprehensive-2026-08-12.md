# MediVU Community 첫 사용자 UX·기능 종합 분석

- 분석일: 2026-08-12
- 대상: `http://localhost:4174/medi-commu/index.html#/home`
- 범위: 환자 게시판, 질문 작성, 내 소식, MY, 비대면 진료 준비, 병원·의사 탐색, 예약, 환자/의사 전환, 화상진료방
- 방식: 390×844 모바일 화면에서 첫 방문부터 실제 조작, 전체 자동 테스트 실행, 관련 코드·데이터 흐름 교차 확인
- 변경 범위: 이 문서만 새로 작성했으며 앱 소스는 수정하지 않음
- 비밀·개인정보: 실제 환자 정보나 실제 의료 내용을 사용하지 않았고, 보고서에도 포함하지 않음

## 1. 결론

MediVU는 이미 단순한 화면 시안을 넘어 **질문 → 의사 답변 → 의사 확인 → 예약/비대면 진료**로 이어지는 제품의 핵심 뼈대를 갖추고 있다. 특히 환자 홈의 상태 변화, 의사 프로필의 신뢰 정보, 예약 단계, 화상진료 중 경고·기록 초안은 방향이 좋다.

다만 현재는 기능 수가 많아서 생기는 문제보다 **무엇을 먼저 해야 하는지, 지금 처리가 어디까지 됐는지, 어떤 데이터가 어디에 저장되는지**가 한눈에 일치하지 않는 문제가 더 크다. 의료 서비스에서는 이 불일치가 일반 커뮤니티보다 훨씬 큰 불안과 이탈을 만든다.

추천하는 제품 한 문장은 다음과 같다.

> 아픈 사람이 30초 안에 안전한 다음 행동을 정하고, 진행 상태를 잃지 않는 앱.

초기 제품은 기능을 더 보여주기보다 아래 한 개의 순환을 빠르고 확실하게 완성하는 편이 좋다.

1. 증상을 평소 말로 적는다.
2. 필요한 질문만 추가로 답한다.
3. 적합한 진료과 또는 의사에게 전달된다.
4. 답변·예약·진료의 현재 상태와 다음 행동을 확인한다.
5. 필요할 때 비대면 진료로 연결된다.

## 2. 전체 기능 점검 결과

표시 기준은 `정상`은 직접 흐름을 완료한 기능, `부분 확인`은 데모 UI 또는 한쪽 사용자까지만 확인한 기능, `문제`는 실제 사용을 막거나 신뢰를 훼손하는 상태다.

| 영역 | 결과 | 확인 내용 |
|---|---|---|
| 첫 진입·참여 안내 | 정상 | 이름·지역 입력, 공유 게시판 및 데모 데이터 안내 확인 |
| 온보딩 | 정상 | 3단계 안내, 건너뛰기/완료, 홈 진입 확인 |
| 환자 홈 | 정상 | 첫 질문 CTA, 준비 상태, 최근 활동, 빠른 메뉴, 상태에 따른 추천 카드 변화 확인 |

| 지도·병원 탐색 | 정상/문제 | 필터와 불가 사유는 좋음. 기준일 고정으로 모든 병원이 휴진처럼 표시됨 |
| 의사 프로필 | 정상 | 경력, 진료 방식, 일정, 위치, 전화, 비대면 가능 여부 확인 |
| 예약 | 정상/개선 필요 | 날짜·시간·서류·확인·예약 목록까지 완료. 저장 안내 문구와 실제 동작이 불일치 |
| Expert 진입 | 정상/문제 | 데모임을 명확히 알림. 다만 환자 계정이 브라우저에서 의사로 승격되는 구조는 출시 불가 |
| 의사 홈·질문 답변 | 정상 | 업무 요약, 받은 질문, 답변 템플릿, 직접 작성, EMR 내보내기 UI 확인 |
| 의사 사연 피드 | 정상 | 맞춤/HOT/읽음/나중에 보기 확인 |
| 의사 예약·진료 요청 | 문제 | 환자가 보낸 요청과 데모 의사 계정이 서로 다른 의사 ID라 종단 간 확인 불가 |
| 화상진료 동의·진료방 | 부분 확인 | 환자/의사 양쪽 진입, 수동 대화 기록, 위험 신호, 진료 기록 초안 확인 |
| 실제 1:1 영상 연결 | 미확인/출시 미준비 | 두 브라우저 간 실제 연결은 완료하지 못함. TURN·재연결·권한 통제가 부족함 |

전체 자동 테스트는 통과했지만, 대부분 데모/메모리 상태의 기능 검증이다. 실제 Supabase 사용자 간 전달, 카메라·마이크, WebRTC 연결, 음성 인식은 자동 테스트 범위에 포함되지 않는다. 따라서 “테스트가 모두 통과했다”와 “실서비스 화상진료가 준비됐다”는 별개의 판단이어야 한다.

## 3. 첫 사용자 관점에서 잘된 점

### 3.1 첫 화면과 온보딩이 부담을 낮춘다

- 첫 참여 화면은 항목이 적고, 가짜 데이터 사용 및 공유 범위를 미리 알려준다.
- 온보딩은 `사연 작성 → 전문의 답변 → 필요 시 진료 연결`이라는 핵심 가치를 짧게 설명한다.
- 119가 필요한 상황을 일반 질문과 구분해 말하는 점은 의료 서비스에 필요한 안전장치다.
- 모바일 폭에서 가로 넘침이 없고 주요 조작 영역도 충분히 크다.

### 3.2 홈이 사용자의 상태에 반응한다

예약 전에는 질문 작성과 준비 상태를 보여주고, 예약 요청 후에는 “예약 희망 시간을 전달했다”는 상태와 다음 행동을 보여준다. 이것은 현재 앱에서 가장 좋은 UX 패턴이다. 토스식 경험의 핵심도 화려한 화면보다 **사용자 상태를 이해하고 다음 한 가지를 분명히 제시하는 것**에 가깝다.

### 3.3 의사 선택 전에 신뢰 정보를 제공한다

의사 프로필에 소개, 진료 방식, 경력, 일정, 위치, 연락처, 비대면 가능 여부가 있다. 환자가 결정을 내리기 직전에 필요한 정보가 배치돼 있다. 단, 앞으로는 면허 인증 방식, 소속기관 확인일, 예상 답변 시간처럼 실제 검증 가능한 신뢰 신호를 우선해야 한다.

### 3.4 예약 과정이 단계적으로 잘 나뉘어 있다

날짜, 시간, 최종 확인이 분리되고 오전·오후·야간 및 점심시간이 구분된다. 필요한 서류를 선택할 수 있는 점도 실제 진료 맥락에 맞다. 긴 질문 작성 화면과 달리 예약은 “한 번에 한 결정”에 가깝게 설계되어 이해하기 쉽다.

### 3.5 비대면 불가 이유를 숨기지 않는다

지도에서 초진 비대면 불가, 오늘 진료 여부 같은 이유를 보여주는 방식이 좋다. 의료에서는 단순히 버튼을 비활성화하는 것보다 **왜 불가능한지와 대신 무엇을 할 수 있는지**가 신뢰를 만든다.

### 3.6 화상진료의 진료 보조 기능은 가능성이 크다

의사 화면에서 대화 내용의 위험 표현을 감지해 응급 안내를 띄우고 진료 기록 초안을 만드는 흐름은 실질적인 가치가 있다. 환자에게는 대화를 대신 판단하는 기능처럼 과장하지 않고, 의사의 확인을 돕는 보조 기능으로 명확히 위치시켜야 한다.

## 4. 가장 먼저 해결해야 할 문제

### P0-1. 환자와 의사의 정체성이 일치하지 않는다

- 환자로 참여한 이름이 MY에 반영되지 않고 별도의 기본 사용자 이름이 표시됐다.
- 데모 의사 템플릿을 선택한 뒤에도 의사 화면 이름이 선택한 의사 이름이 아니라 환자 참여 이름으로 표시됐다.
- 진료과가 일부 화면에서 `otolaryngology`처럼 내부 영문 값으로 노출됐다.
- 환자 화면으로 돌아가도 서버 프로필 역할과 화면의 역할이 서로 달라질 수 있는 구조다.

의료 서비스에서 “지금 누구로 접속해 있는가”가 흔들리면 다른 모든 신뢰 장치가 무너진다. 테스트를 위해 두 역할을 한 앱에 둔다면 제품 안의 Expert 버튼보다 **테스트 전용 계정 선택기**로 분리하는 것이 안전하다.

### P0-2. 환자 요청이 같은 의사에게 도착하는 종단 간 흐름을 검증할 수 없다

환자 쪽에서 특정 의사에게 예약과 비대면 진료를 요청했지만, Expert 데모로 만든 의사는 새 계정이어서 받은 요청이 0건이었다. 현재 구조에서는 “환자가 A 의사에게 요청 → A 의사가 받음 → A 의사가 진료방 입장”을 한 흐름으로 테스트하기 어렵다.

출시 전에는 고정된 테스트 환자·테스트 의사 쌍을 제공하고 아래를 자동화해야 한다.

1. 환자가 의사를 선택한다.
2. 예약 또는 진료 요청이 동일한 의사 ID에 저장된다.
3. 해당 의사 계정에 즉시 노출된다.
4. 양쪽이 같은 진료방 ID에 들어간다.
5. 완료 후 양쪽 상태가 동일하게 갱신된다.

### P0-3. 실제 저장 방식과 안내 문구가 다르다

예약과 질문 화면 일부는 “브라우저 메모리에만 저장”한다고 안내하지만, 현재 라이브 모드에서는 Supabase에 데이터를 전송한다. 반면 사전 확인 일부는 실제로 로컬 저장이다.

의료 데이터에서는 이 차이가 UI 문구 문제가 아니라 동의와 신뢰의 문제다. 각 입력 직전에 다음을 짧고 정확하게 알려야 한다.

- 누가 볼 수 있는가
- 서버에 저장되는가
- 얼마나 보관되는가
- 사용자가 삭제할 수 있는가
- 공개 게시판과 진료 요청의 차이는 무엇인가

### P0-4. 질문 작성 실패가 사용자에게 보이지 않는다

질문 제출을 시도했을 때 작성 화면은 그대로 남았고 실패 이유가 보이지 않았다. 다른 화면으로 이동한 뒤에야 데이터베이스의 원문 오류가 상단에 나타났다. 집중 작성 화면에서 공통 헤더를 숨기면서, 오류 표시까지 함께 숨겨진 구조다.

사용자에게는 필드 가까이 “진료 날짜를 확인해 주세요”처럼 행동 가능한 한국어 안내가 필요하다. 데이터베이스 원문은 화면에 노출하지 않아야 한다. 실패 시 입력 내용이 유지된다는 확인도 필요하다.

### P0-5. 일정 기준일이 고정돼 있다

데모 진료 일정의 기준일이 2026-08-09로 고정돼 있어 분석일인 2026-08-12에는 병원이 모두 “오늘 휴진”으로 보였고, 예약 후보에도 지난 날짜가 섞였다. 시간과 일정은 의료 앱의 기본 신뢰 신호다. 사용자 기기의 현재 날짜·시간대 또는 서버 기준 시간을 사용하고, 과거 시간은 선택할 수 없게 해야 한다.

### P0-6. 화상진료는 데모로는 유효하지만 실서비스 준비가 부족하다

화상진료방 화면, 동의, 대화 기록, 수동 입력, 위험 신호, 기록 초안은 확인했다. 그러나 실제 영상 연결은 다음 이유로 운영 준비 상태로 볼 수 없다.

- 공용 STUN만 있고 TURN 중계 서버가 없다.
- 상대 설명보다 먼저 도착한 ICE 후보를 보관하지 않고 버릴 수 있다.
- 연결 제한시간, 재시도, 재접속, 네트워크 품질 안내가 없다.
- 방 ID를 아는 사용자의 참여를 막는 명확한 방 권한 검사가 보이지 않는다.
- 카메라·마이크 사전 점검과 장치 선택이 없다.
- 음성 인식은 브라우저 제공자에게 음성이 전송될 수 있으며, 데모 안내는 있지만 실서비스 대안이 필요하다.
- 실제 두 사용자 간 연결을 검증하는 테스트가 없다.

실서비스 전 최소 기준은 인증된 예약 참여자만 입장, 짧은 수명의 참여 토큰, TURN, ICE 후보 큐, 연결 시간 제한과 재시도, 카메라·마이크 사전 점검, 네트워크 저하 안내, 재접속, 두 브라우저 E2E 테스트다.

### P0-7. 데모 의사 전환이 실제 권한 상승과 너무 가깝다

현재 브라우저에서 사용자가 자기 프로필 역할과 의사 인증 상태를 바꾸는 데모 흐름이 실제 데이터 계층과 연결돼 있다. 공유 테스트 환경에서는 편리하지만 공개 출시 구조로는 사용할 수 없다. 데모 전환은 별도 환경 또는 테스트 계정에만 허용하고, 운영 환경의 의사 권한은 서버 관리자가 검증된 계정에만 부여해야 한다.

## 5. 질문 작성 UX 분석

현재 질문 1단계에는 제목, 본문, 날짜, 경과, 신체 부위, 통증 정도, 시간대, 복용약, 알레르기, 일상 영향, 시도한 방법, 여러 추가 질문이 한 화면에 있다. 기본 상태에서만 버튼 24개, 입력 요소 26개, 질문 묶음 8개 수준이다. 사용자가 아프고 불안한 상태라는 점을 고려하면 지나치게 높은 인지 부담이다.

더 큰 문제는 사용자가 `코·목·귀`를 선택했는데 여성 건강 관련 질문과 생리 시작일이 나타날 수 있다는 점이다. 선택 부위와 자동 추론 결과를 항상 합치는 현재 방식 때문에, 분류기가 확신하지 못한 민감 질문이 노출될 수 있다.

추천 흐름은 다음과 같다.

1. **무엇이 가장 불편한가요?** 자유 입력 하나
2. **언제부터 그랬나요?** 짧은 선택
3. 답변에 꼭 필요한 질문만 2~4개 동적으로 제시
4. 복용약·알레르기 등은 “추가하면 답변에 도움이 돼요”로 접기
5. 공개 범위 선택
6. 게시 전 전체 요약 및 수정

자동 추론은 명확한 확신 기준을 넘을 때만 추가 질문을 보여주고, 민감 질문은 먼저 “관련 질문을 해도 될까요?”라고 동의를 받아야 한다. 사용자가 신체 부위를 직접 골랐다면 그 선택을 우선하고, 자동 추론은 보조 제안으로만 사용해야 한다.

현재 공개 범위 선택 자체는 좋지만 기본값이 공개다. 의료 질문은 `진료과 의료진만`을 기본으로 하고, 공개 게시를 선택할 때만 이름 노출 방식과 공개 범위를 한 번 더 명확히 알려주는 편이 안전하다.

마지막 확인 화면에는 현재 진료과 판단만 보인다. “게시 후 수정 불가”라면 반드시 제목, 증상, 날짜, 주요 답변, 첨부, 공개 범위를 모두 요약하고 각 항목에 수정 버튼을 제공해야 한다.

## 6. 정보량이 많으면 의료에서도 불편한가

그렇다. 오히려 의료에서 더 민감하다. 사용자는 통증, 걱정, 시간 압박, 개인정보 노출 우려를 동시에 가지고 있어 평상시보다 읽고 결정할 여력이 적다.

하지만 의료 정보를 단순히 삭제하면 안 된다. 적용 원칙은 **정보 축소가 아니라 단계적 공개**다.

| 우선순위 | 화면에 보이는 방식 | 예시 |
|---|---|---|
| 1. 결론 | 첫 문장으로 바로 표시 | “지금은 이비인후과 상담이 적합해 보여요” |
| 2. 다음 행동 | 가장 큰 버튼 하나 | “증상 보내기”, “예약 시간 선택” |
| 3. 상태 | 짧은 타임라인 | 접수됨 → 의사 확인 중 → 답변 도착 |
| 4. 이유 | 펼쳐보기 | 왜 이 진료과인지, 왜 비대면 불가인지 |
| 5. 법적·의학적 상세 | 결정 시점에 표시 | 동의, 보관, 부작용, 응급 안내 |

항상 보여야 하는 정보도 있다. 의사 인증 여부, 비용, 공개 범위, 데이터 수신자, 응급 시 119 안내, 최종 동의는 접어 숨기면 안 된다. 즉 **안전·신뢰 정보는 선명하게, 설명·보조 정보는 필요할 때 펼치게** 하는 것이 적절하다.

## 7. 홈과 내비게이션 추천

### 7.1 홈은 게시물 피드보다 “다음 행동” 중심이 적합하다

공감 글을 홈에서 제외하려는 방향에 동의한다. 첫 사용자가 홈에서 보고 싶은 것은 다른 사람의 글보다 “나는 지금 무엇을 하면 되는가”다.

추천 홈 구성은 세 덩어리면 충분하다.

1. **오늘의 다음 행동 카드**
   - 처음: “어디가 불편한지 알려주세요”
   - 작성 후: “의사가 확인 중이에요”
   - 답변 후: “답변이 도착했어요”
   - 예약 후: “8월 13일 오전 10:30 진료 예정”
2. **내 진행 상황**
   - 질문, 답변, 예약, 비대면 진료를 하나의 짧은 타임라인으로 표시
3. **빠른 도움**
   - 병원 찾기, 비대면 준비, 응급 안내 정도만 노출

HOT 사연과 건강 콘텐츠는 홈 핵심이 아니라 필요하면 아래쪽의 작은 보조 영역 또는 사연 탭으로 보내는 편이 좋다.

### 7.2 하단 내비게이션

현재 `홈 · 사연 · Q · 지도 · MY`는 이해하기 쉽지만, 답변 도착이 제품의 보상 순간이라는 점에서 `내 소식`의 발견성이 부족하다. 헤더의 종 아이콘만으로는 초보 사용자가 기능을 놓치기 쉽다.

추천은 `홈 · 사연 · Q · 내소식 · MY`다. 지도/병원 찾기는 홈의 빠른 도움과 의사 선택 흐름 안에서 제공한다. 중앙 Q는 지금처럼 가장 크고 분명하게 유지한다. 새 답변·예약 변경에는 종 아이콘과 탭에 숫자 배지를 함께 쓰는 편이 좋다.

## 8. MY와 비대면 준비 추천

현재 MY는 4단계 진행 목록과 아래 준비 메뉴가 반복되어 길다. 비대면 진료 사전 확인을 버튼 하나로 축소하고 별도 화면으로 보내는 방향이 적합하다.

추천 MY 구조는 다음과 같다.

- 프로필: 이름, 생년 정보, 연락처, 본인 인증
- 진료 준비: 비대면 진료 사전 확인, 주소, 결제수단, 보험/서류 정보
- 진료 관리: 예약, 진료 내역, 처방전·서류, 관심 의료진
- 앱 설정: 알림, 개인정보 공개, 차단·신고, 접근성, 온보딩 다시 보기
- 고객 지원: 이용 안내, 의료 분쟁/문의, 약관, 개인정보 처리방침
- 테스트 전용: 데모 초기화와 역할 전환은 운영 UI와 시각적으로 분리

홈에서는 준비 상태를 `3/4`처럼 보여주되, 지금 진료에 필요한 한 항목만 CTA로 제시하면 충분하다.

## 9. 토스·카카오톡 및 해외 성공 제품에서 가져올 원칙

특정 화면을 복제하기보다 성공한 초기 제품들의 공통 작동 원리를 적용하는 편이 좋다.

### 토스형 원칙

- 복잡하고 불안한 일을 한 문장과 한 버튼으로 시작하게 한다.
- 완료 직후 결과와 다음 상태를 명확하게 보여준다.
- 전체 기능 메뉴보다 현재 사용자에게 필요한 행동을 먼저 보여준다.

### 카카오톡·WhatsApp형 원칙

- 처음부터 학습 없이 이해되는 익숙한 구조를 쓴다.
- 반응이 도착했다는 보상을 강하게 알린다.
- 반복 사용의 이유를 기능 수가 아니라 관계와 응답의 순환에서 만든다.

### 예약·원격진료 제품형 원칙

- 의료진의 실제 검증 정보, 가능한 시간, 비용, 진행 상태가 꾸밈보다 중요하다.
- “접수됐는가, 누가 확인 중인가, 언제 답이 오는가”를 계속 보여준다.
- 연결이 안 될 때 대체 행동과 지원 경로를 즉시 제공한다.

MediVU에 맞춘 표현으로 요약하면 다음과 같다.

> 첫 화면은 기능 안내가 아니라 안심, 질문 작성은 문진표가 아니라 대화, 답변 도착은 알림이 아니라 다음 행동의 시작이어야 한다.

## 10. 환자·의사 앱 분리 방향

출시 시 분리한다는 계획이 적절하다. 환자와 의사는 사용하는 목적, 용어, 법적 책임, 정보 밀도가 완전히 다르다.

- 환자 앱: 불안 감소, 쉬운 질문, 답변·예약 상태, 진료 준비
- 의사 앱: 업무 큐, 안전 분류, 답변 효율, 진료 기록, 일정 관리

지금처럼 함께 테스트해야 한다면 제품 화면 안에서 역할을 바꾸기보다 다음 중 하나를 추천한다.

1. 브라우저 프로필 두 개에 고정 환자/의사 테스트 계정 제공
2. 개발 환경에만 보이는 테스트 역할 선택기 사용
3. “이 의사로 로그인”이 아니라 “A 의사에게 보낸 요청을 A 의사 화면에서 열기”라는 고정 시나리오 제공

운영 빌드에서는 역할 전환 코드와 데모 권한 상승 경로가 포함되지 않도록 빌드 단계에서 차단해야 한다.

## 11. 우선순위 로드맵

### P0 — 신뢰와 종단 간 동작

1. 환자/의사 프로필과 역할의 단일 진실 원천 확립
2. 환자 → 동일 의사 → 동일 진료방 E2E 시나리오 구축
3. 실제 저장·공개·보관 방식에 맞춘 개인정보 문구 정정
4. 질문 제출 오류의 화면 내 한국어 안내 및 입력 보존
5. 현재 날짜·시간 기반 일정으로 교체
6. 운영 환경 의사 권한을 서버 검증으로 제한
7. 화상진료 인증, TURN, 재연결, 장치 점검, 양방향 E2E 보강

### P1 — 첫 사용과 재방문

1. 질문 1단계를 필수 최소 항목 중심으로 축소
2. 민감 추가 질문에 동의·확신 기준 적용
3. 질문 공개 범위를 비공개 중심으로 변경
4. 게시 전 전체 요약과 항목별 수정 제공
5. 내소식을 하단 탭에 배치하고 답변 배지 제공
6. 모든 제출 후 성공 영수증과 상태 타임라인 제공
7. MY 중복 제거 및 사전 확인을 별도 버튼으로 축소

### P2 — 콘텐츠와 완성도

1. 데모 데이터와 공유 테스트 데이터를 명확히 분리
2. 목록의 테스트성 제목·잡음을 정리하고 자동 만료 적용
3. 사연 검색, 저장, 신고·차단 보강
4. 진료과·상태·버튼 용어를 일관된 한국어로 통일
5. 키보드 포커스, 스크린리더, 큰 글자, 축소 모션 검증

### P3 — 실제 출시 기능

1. 실제 결제, 처방전·증명서 전달, 푸시 알림
2. 운영용 의사·기관 인증과 감사 로그
3. 의료정보 보관·삭제·철회 정책 및 동의 이력
4. 장애 대응, 상담 지원, 화상진료 품질 모니터링

## 12. 다음 버전의 검증 가능한 완료 기준

- 첫 사용자가 도움 없이 60초 안에 첫 질문 초안을 만들 수 있다.
- 첫 질문 필수 입력은 한 화면에서 5개 이하의 결정으로 끝난다.
- 민감 질문은 관련성 확인 또는 사용자 동의 없이 나타나지 않는다.
- 기본 공개 범위가 의료진 한정이며, 공개 선택 시 범위를 명시한다.
- 질문·예약 제출 성공 또는 실패가 같은 화면에서 즉시 이해되는 한국어로 표시된다.
- 환자가 요청한 의사 계정에 5초 이내 요청이 나타나고 동일 방에 입장할 수 있다.
- 환자와 의사 화면의 이름, 역할, 진료과가 모든 경로에서 일치한다.
- 과거 날짜와 휴진 시간은 예약할 수 없다.
- 두 개의 실제 브라우저에서 영상·음성 연결, 권한 거절, 네트워크 단절, 재접속을 자동 검증한다.
- 화면의 저장·공개 안내와 네트워크에서 실제 일어나는 동작이 일치한다.
- 360×800, 390×844, 768px, 1280px에서 가로 넘침과 가려진 하단 버튼이 없다.

## 13. 분석 중 확인된 제한과 주의사항

- 자동 테스트는 31개 파일, 241개 항목이 통과했지만 연속 2회 실행 조건은 이번 분석 범위에서 수행하지 않았다.
- 실제 두 사용자 간 카메라·마이크 영상 연결은 완료하지 못했으므로 화상 품질을 정상으로 판정하지 않았다.
- 결제와 푸시 알림은 설정·진입 수준이며 실제 외부 결제/전송을 검증하지 않았다.
- 질문 등록 시 발생한 빈 날짜 오류는 자동화 입력 이벤트의 영향 가능성도 있으나, 실패 안내가 작성 화면에 나타나지 않고 원시 오류가 뒤늦게 노출되는 UX 결함은 별도로 확인됐다.
- 공유 테스트 환경에 가짜 테스트 예약·비대면 요청이 남아 있을 수 있다. 실제 사용자 데이터는 입력하지 않았다.

## 최종 판단

현재 MediVU의 경쟁력은 게시판의 콘텐츠 양이 아니라 **환자가 질문을 시작한 뒤 실제 진료까지 연결할 수 있는 구조**에 있다. 다음 단계에서 화면을 더 꾸미거나 기능을 더 추가하기보다, 정체성·개인정보·전달 상태·영상 연결의 진실성을 먼저 고치고 질문 과정을 과감하게 줄이는 것이 가장 효과적이다.

좋은 목표는 “의료 기능이 많은 앱”이 아니다. 사용자가 불안할 때 열어도 길을 잃지 않고, 의료진에게 안전하게 연결됐다는 확신을 주는 앱이다.
