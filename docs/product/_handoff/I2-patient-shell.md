## 이 구간이 하는 일

**D-1이 정한 제품의 축을 화면으로 만든다.** 공개 Q&A가 축이라면 홈이 사연 피드여야 하고, 재방문의 이유(답변 도착)가 탭이어야 하며, 갈 곳을 아는 환자의 길이 따로 있어야 한다.

| # | 항목 |
| --- | --- |
| **G-1** | `/home`을 **사연 피드 + 진행 상태 스트립**으로. 지금은 `resolveNextStep` 대시보드 |
| **G-4** | `/news`를 탭 화면으로. 「내 사연」 흡수 |
| **G-3** | `/care` 채우기 — 지도 + 재진 두 출처 + 예정된 예약 |
| **G-9** | **위 세 화면의 정렬 기준을 화면에 공개** |

## 반드시 지킬 것

### 진행 상태 스트립 (G-1)

D-5의 비용을 갚는 장치다. **홈을 상태에 따라 바꾸지 않는다** — 홈이 사람마다 다르면 설명도 테스트도 어려워진다.

- 사연 피드 **위**에 고정
- 진행 중인 건이 있을 때만 나타난다. 없으면 자리도 차지하지 않는다
- `답변 도착 n건` · `예약 예정` · `진료방 열림` 중 **가장 급한 하나**
- **`encounterTrack`이 이미 이 데이터를 만든다.** 새로 계산하지 마라
- `resolveNextStep`을 지우지 말고 **스트립이 쓰도록 옮긴다** — 우선순위 판단이 거기 있다

### 재진의 두 출처 (G-3)

| 출처 | 어디서 | 신뢰 등급 |
| --- | --- | --- |
| 앱 내 이력 | `bookings` · `encounters` 조회 | 검증됨 |
| 환자 직접 등록 | `self_reported_clinics` | **검증 안 됨** |

**두 출처를 섞어 보여 주지 마라.** 검증되지 않은 것이 검증된 것처럼 보이면 P1의 실패 조건(「화면이 자기 말을 대신 만들어 낸 것이 된다」)과 같은 배신이다. 화면에서 등급을 구분해 표시한다.

「불러오기」(의료기관 연계)는 **자리만 남기고 만들지 않는다.**

### 정렬 기준 공개 (G-9)

**C-2 파생 규칙 3이다. 취향이 아니다.** 돈을 안 받아도 정렬이 선택을 유도하면 개정 의료법 제34조의9에 걸린다.

`30-feature-spec.md` §정렬 기준과 C-2 판정 표에 화면별 정렬 기준이 이미 적혀 있다. **그것을 화면에 한 줄로 노출한다.** 새로 정하지 마라.

**G-9를 따로 하지 않는 이유** — 이 세션이 그 화면들을 이미 다시 쓴다. 나중에 하면 같은 파일을 두 번 연다.

## 하지 말 것

- **「추천」·「당신에게 맞는」·「인기」를 만들지 마라.** IA §5의 「두지 않는 것」이고 C-2 위반이다
- 답변 본문 안에 예약 버튼을 두지 마라 — 답변과 예약은 분리한다
- 비공개 덧붙임을 만들지 마라. 그건 G-5이고 I5다
- `BottomNav.tsx`·`App.tsx`를 만지지 마라 — I1이 확정했다
- 진단명·확률·중증도를 출력하지 마라 (C-5)

## 확인

브라우저로 본다(`.claude/launch.json`의 `medivu-dev`, 375×812).

- 홈이 사연 피드인가. 진행 중인 건이 없을 때 스트립이 **자리를 안 차지하는가**
- `/care` 세 구역이 다 있는가. 두 출처가 **구분되어** 보이는가
- 세 화면에 정렬 기준이 한 줄로 보이는가
- **빈 화면** — 사연이 0개일 때, 진료 이력이 0개일 때 무엇이 보이는가. 무료 커뮤니티는 초기에 전부 비어 있다

## 끝났다고 판단하는 기준

1. G-1·G-3·G-4·G-9가 화면에서 동작한다
2. 다섯 상태(비어 있음 / 불러오는 중 / 정상 / 오류 / 권한 없음)가 세 화면에 다 있다
3. 두 출처가 등급 구분되어 보인다
4. 정렬 기준이 세 화면에 공개돼 있다
5. `npm run test:run` 통과 + **바뀐 화면의 플로우 테스트를 더했다**
6. `30-feature-spec.md`의 해당 절과 코드가 어긋나지 않는다 — 어긋나면 **코드가 아니라 문서를 고칠지 먼저 판단한다**
