## 1. 원칙

### IA-1 · 두 진입로를 섞지 않는다

환자는 두 상태 중 하나로 앱을 연다. **상태가 다르면 필요한 화면이 다르다.**

| | 의사 찾기 | 주변·재진 |
| --- | --- | --- |
| 환자 상태 | 볼 의사를 **모른다** | 볼 의사를 **안다** |
| 하는 일 | 사연을 쓰고, 모인 답변에서 스스로 고른다 | 지도나 진료 이력에서 바로 예약·비대면 신청 |
| 걸리는 시간 | 답변을 기다린다 (비동기) | 즉시 |
| 홈 기본값 | **예** (D-5) | 아니오 — 별도 탭 |

한 화면에서 둘을 다 처리하려 하면 둘 다 흐려진다.

### IA-2 · 아픈 사람의 불안을 줄이는 정보는 늘린다

`05-decisions.md` P-1. 입력 칸·결정 횟수는 줄이되, **진행 상태·근거·다음에 일어날 일은 늘린다.** 힉의 법칙을 이 도메인에 그대로 적용하지 않는다.

구체적으로 — **내 요청이 지금 어디까지 왔는지는 어느 화면에서든 두 번 안에 닿아야 한다.**

### IA-3 · 플랫폼이 의사를 고르는 자리를 만들지 않는다

C-2. 의사 목록의 기본값은 **전체 목록 + 중립 필터**(진료과·거리·예약 가능 여부)다. "추천", "당신에게 맞는", "인기" 같은 묶음은 IA에 존재하지 않는다. 없는 화면은 실수로 만들어질 수 없다.

키워드 매칭은 **사연 → 의사 인박스** 방향으로만 흐른다. 그 반대 방향(환자에게 의사를 골라 주는)은 만들지 않는다.

### IA-4 · 두 정체성은 트리를 공유하지 않는다

같은 계정이 환자로도 의사로도 참여한다. `/`와 `/doctor/`는 **별개의 트리**이며 탭도 따로 갖는다. 섞이면 환자가 누구에게 묻는지 잘못 판단한다.

## 2. 최상위 구조 — 탭 재편 **[채택 · 2026-08-27]**

D-5로 홈의 기본이 사연 피드가 되면서 **기존 `홈`과 `사연` 탭이 같은 것을 가리키게 됐다.** 그대로 둘 수 없다.

### 환자 탭

| # | 탭 | 라우트 | 담당 | 현재와 비교 |
| --- | --- | --- | --- | --- |
| 1 | **홈** | `/home` | 사연 피드 (의사 찾기) + 진행 상태 스트립 | **역할 변경** — 대시보드 → 피드 |
| 2 | **내 소식** | `/news` | 내 사연과 도착한 답변 | **탭으로 승격** — 현재는 헤더 종 아이콘 |
| 3 | **Q** | `/ask` | 사연 작성 (중앙 버튼) | 유지 |
| 4 | **진료** | `/care` | 지도 + 내가 진료봤던 곳 + 예정된 예약·진료방 | **신설** — 현재 `/map` 확장 |
| 5 | **MY** | `/me` | 설정 | 유지 |

**없어지는 것:** `사연` 탭 (홈이 그 역할을 가져감).

### 왜 이렇게 바꾸나

- **`내 소식`을 탭으로 올리는 이유** — 무료 커뮤니티에서 재방문의 이유는 하나다. **내 사연에 답이 달렸는가.** 그 보상을 헤더 종 아이콘에 두면 앱의 심장이 부속으로 밀린다. D-1이 Q&A를 축으로 정한 이상 여기는 탭이어야 한다.
- **`지도`를 `진료`로 넓히는 이유** — IA-1의 두 번째 진입로 전체가 여기 들어간다. 지도(주변)와 진료 이력(재진)은 **"볼 의사를 아는 환자"라는 같은 상태**를 다룬다. 별개 탭 두 개로 쪼개면 5개 자리에 안 들어가고, 사용자에게도 같은 일이 두 곳에 있는 것처럼 보인다.
- **`홈`이 대시보드를 잃는 대신** — 진행 상태 스트립이 그 역할을 이어받는다. 아래 참조.

### 진행 상태 스트립

D-5의 비용(갈 곳을 아는 환자에게 한 단계가 늘어남)을 홈을 상태별로 바꾸지 않고 푸는 장치다. **홈이 사람마다 다르면 설명도 테스트도 어려워진다.**

- 위치: `/home` 사연 피드 **위**, 고정
- 조건: 진행 중인 건이 있을 때만 나타난다. 없으면 자리도 차지하지 않는다
- 내용: `답변 도착 n건` · `예약 예정` · `진료방 열림` 중 **가장 급한 하나**
- 동작: 누르면 해당 화면으로 직행
- 근거: IA-2. 아픈 사람이 자기 요청의 생사를 확인하는 최단 경로

`encounterTrack`의 4단계 추적이 이미 이 데이터를 만든다. 새로 계산할 것이 없다.

### 의사 탭 — 변경 없음

| # | 탭 | 라우트 | 담당 |
| --- | --- | --- | --- |
| 1 | 홈 | `/doctor/home` | 오늘 할 일 요약 |
| 2 | **받은 질문** | `/doctor/inbox` | 내 과·내 키워드에 걸린 사연. **의사 앱의 중심** |
| 3 | 사연 | `/doctor/stories` | 전체 피드 |
| 4 | 진료 | `/doctor/visits` | 예약·비대면 일정 |
| 5 | MY | `/doctor/me` | 프로필·키워드·비대면 설정 |

D-1이 Q&A를 축으로 정했으므로 **`받은 질문`이 의사 앱의 중심**이다. 하루 답변 상한 **5회**(D-8)의 잔여 횟수와 초기화 시점을 이 화면 상단에 상시 노출한다 — 상한은 감추는 제약이 아니라 **드러내는 자원**이다. 언제 다시 채워지는지 모르면 희소성이 아니라 그냥 막힘이다.

## 3. 화면 지도

`신설` = 화면이 없음 · `변경` = 있으나 역할이 달라짐 · `유지` = 그대로

### 환자

```
/onboarding                        게이트 · 유지
│
├─ /home                           홈 = 사연 피드           변경
│  ├─ [진행 상태 스트립]                                     신설
│  └─ /questions/:questionId       사연 상세                유지
│     ├─ 답변 목록 (전체, 정렬 공개)
│     ├─ 비공개 덧붙임              D-6 · 구조 강제 6항목     신설
│     └─ /doctors/:doctorId        의사 프로필              변경 (C-3)
│
├─ /news                           내 소식 = 내 사연과 답변  변경 (탭 승격)
│
├─ /ask                            사연 작성 3단계          유지
│
├─ /care                           진료 (주변 · 재진)       신설
│  ├─ 지도 (← 현재 /map)           주변 의원               변경
│  ├─ 내가 진료봤던 곳              재진 · 두 출처           신설
│  │  ├─ 앱 내 이력 (자동)          bookings · encounters
│  │  └─ 환자 직접 등록 (수동)      검증 안 됨 · 등급 구분
│  ├─ 예정된 예약·진료방            ← /me/appointments 흡수
│  ├─ /booking/:doctorId           대면 예약 3단계          유지
│  ├─ /me/precheck                 비대면 사전 확인         유지
│  └─ /visit/:roomId               화상 진료방              유지
│
└─ /me                             MY                     유지
   └─ /me/address /notifications /privacy
```

**리다이렉트로 남기는 것:** `/map` → `/care` · `/stories` → `/home` · `/me/appointments` → `/care`.
셋 다 흡수됐지만 기존 링크와 북마크가 살아 있어야 한다.

### 재진의 두 출처 (Q-4)

| 출처 | 어디서 오나 | 신뢰 등급 |
| --- | --- | --- |
| **앱 내 이력** | `bookings` · `encounters` 조회. 자동 | 검증됨 — `clinics`를 가리킨다 |
| **환자 직접 등록** | 환자가 "여기 다니고 있어요"를 손으로 추가 | **검증 안 됨** — 화면에서 구분해 표시한다 |

앱 내 이력만 두면 신규 사용자의 재진 섹션이 영원히 비어 있고, IA-1의 두 번째 진입로가 처음부터 죽는다. 그래서 직접 등록을 연다. **대신 두 출처를 섞어 보여 주지 않는다** — 검증되지 않은 데이터가 검증된 것처럼 보이면 안 된다.

**추후 확장 (지금 만들지 않음):** 의료기관 연계를 통한 "불러오기". 자리만 남기고 화면은 만들지 않는다.

### 의사

```
/doctor/home                       홈                      유지
├─ /doctor/inbox                   받은 질문 + 잔여 답변 횟수  변경
│  └─ /doctor/questions/:id        답변 작성                유지
├─ /doctor/stories                 사연 피드                유지
├─ /doctor/visits                  진료                    유지
│  └─ /doctor/visit/:roomId        화상 진료방              유지
└─ /doctor/me                      MY                      유지
   └─ /doctor/me/profile /keywords /telemedicine
```

## 4. 이동 규칙

### 셸이 사라지는 화면

헤더와 하단 탭을 **숨기는** 화면은 "지금 이것만 하는" 화면이다. 여기서 나가려면 명시적으로 나가야 한다.

| 화면 | 왜 숨기나 |
| --- | --- |
| `/onboarding` · `/expert` | 게이트. 통과 전에는 다른 곳이 없다 |
| `/ask` | 3단계 작성. 중간 이탈이 곧 미완성 사연이다 |
| `/visit/:roomId` · `/doctor/visit/:roomId` | 통화 중. 실수로 나가면 상대가 혼자 남는다 |
| `/me/precheck` · MY 설정 5종 | 한 화면 한 목적 |

### 뒤로 가기

- 탭 사이 이동은 히스토리를 쌓지 않는다
- 3단계 작성(`/ask`, `/booking`)의 뒤로 가기는 **단계 뒤로**이며, 1단계에서의 뒤로 가기는 이탈 확인을 받는다
- 진료방에서의 뒤로 가기는 **나가기 확인**을 받는다

### 모달·바텀시트를 쓰는 자리

되돌릴 수 없는 동작의 확인, 그리고 **본문 흐름을 끊지 않아야 하는 보조 정보**에만 쓴다. 모달 안에 새 결정을 만들지 않는다 — 모달은 라우트가 없어서 뒤로 가기가 안 통한다.

## 5. 두지 않는 것

C-2와 IA-3의 결과다. **이 목록은 취향이 아니라 규제다.** 추가하려면 `05-decisions.md`를 먼저 고쳐야 한다.

| 두지 않는 것 | 이유 |
| --- | --- |
| "추천 의사" · "당신에게 맞는 의사" · "인기 의사" 섹션 | 제34조의9 선택 유도 |
| 답변 품질·평점 기반 의사 랭킹 화면 | 〃 |
| 의사 프로필의 평점·후기·전후사진·가격·홈페이지 링크 | C-3 (제57조3항 심의 예외 이탈) |
| 답변 본문 안의 예약 버튼 | 답변과 예약은 시각적·기능적으로 분리 |
| 결제·구독·상단 노출 구매 화면 | D-4 |
| 약 배송 화면 | 범위 밖 (약사법) |
| 진단명·질병 확률·중증도 지수 | C-5 |
| 의원 운영자용 화면 | D-1로 범위 밖. P3은 대상 아님 |

**답변 본문과 예약의 관계** — 사연 상세에서 답변을 읽고 그 의사에게 가려면 `의사 프로필`을 한 번 거친다. 이 한 단계는 마찰이 아니라 **분리의 증거**다. 없애지 않는다.

### 7.0 · 무엇을 봤나

| 대상 | 방법 | 날짜 |
| --- | --- | --- |
| **세무통** `client.semutong.com` · 앱 3.6.4 | 공개 API(`/api/proxy/v2/*`) 응답 · JS 번들 전수 · 웹뷰 브리지 | 2026-08-31 |

세무통은 **분야만 다른 같은 구조**다 — 비전문가가 사연을 쓰고, 자격자가 답하고, 답변에서 프로필로 넘어간다. 닥터나우는 **같은 분야에서 반대 선택을 한 사례**다. 앞의 것에서는 구조를 가져오고, 뒤의 것에서는 가지 않을 길을 확인한다.

### 7.1 · 되돌리기가 싼 것 — 시제품에 넣어도 된다

되돌리기 비용의 기준은 **데이터가 남느냐**다. 아래 항목은 UI 층이라 스키마에 흔적을 남기지 않는다. 빼도 아무도 다치지 않는다.

| ID | 무엇 | 놓을 자리 | 왜 | 제거 조건 |
| --- | --- | --- | --- | --- |
| **G1** | **의사·의료기관 검색** | `/care` · 의사 목록 | IA-1의 두 번째 진입로를 지금은 지도와 진료 이력 둘로만 받는다. **이름은 아는데 위치를 모르는 환자에게 진입로가 없다.** 세무통은 `/experts` 검색바가 이 자리를 받는다 | 4주간 검색 사용률이 진입로 중 최하위일 때 |
| **G2** | **비로그인 열람** | `/home` · `/questions/:id` 읽기 전용 | 무료 커뮤니티에서 **답변이 쌓인 걸 보기 전에는 가입할 이유가 없다.** 현재는 「가입해야 볼 수 있는데, 볼 게 있는지는 가입해야 안다」가 된다. 세무통은 개인 데이터(`/chat`)에서만 게이트를 건다 | 비로그인→가입 전환이 게이트 방식보다 낮을 때 |
| **G3** | 사연 작성 상황 프리셋 | `/ask` 1단계 | 백지 공포를 줄인다. IA-2와 정합. 세무통 `/bid-request`는 상황 문장 9종을 먼저 보여준다 | 프리셋 선택률이 낮거나 자유 서술 품질이 떨어질 때 |
| **G4** | 절차 지식 문서 | 신설 또는 `/home` 하단 | 답변을 기다리는 동안의 이탈을 줄인다. IA-2가 요구하는 쪽 | 체류에 기여하지 않을 때 |
| **G5** | 의사 저장 | 의사 프로필 · `/care` | 재진 진입로 보조. 환자가 직접 담으므로 플랫폼이 고르는 게 아니다 | 저장 후 재방문이 없을 때 |
| **G6** | 플랫폼 누적 지표 | `/home` 또는 `/onboarding` | 「지금까지 사연 n건 · 답변 n건」. **개별 의사 지표가 아니라 플랫폼 전체 지표**라 C-2·C-3 밖이다 | 숫자가 초라해서 역효과일 때 |
| **G7** | 사연 공유 | `/questions/:id` | 현재 문서는 「공유 링크로 들어온 사람」의 복귀만 다루고 공유 버튼은 명세가 없다 | — 아래 경계 참조 |

**규제 경계 — 넣을 때 반드시 같이 그을 선**

| ID | 경계 |
| --- | --- |
| G1 | **검색은 C-2 위반이 아니다.** IA-3이 금지한 것은 *플랫폼이 만든 묶음*(추천·인기·당신에게 맞는)이다. 검색은 **질의를 환자가 만든다.** 단 자동완성이 의사 이름을 먼저 제안하기 시작하면 그때부터는 묶음이다 |
| G3 | 프리셋이 **진료과로 자동 매핑되면 그 순간 플랫폼이 고른 것**이 된다. 프리셋 → 키워드까지만 허용하고 진료과 확정은 환자가 한다. IA-3의 「키워드는 사연 → 의사 인박스 방향으로만」과 이어진다 |
| G4 | C-5가 진단명·질병 확률·중증도를 막는다. **증상 지식은 쓰지 않는다.** 절차 지식만 쓴다 — 「비대면 진료는 언제 되나」 「진료과를 모를 때」 「예약 확정은 언제」 |
| G7 | 사연에는 증상이 들어 있다. 공유는 **민감정보를 앱 밖으로 내보내는 동작**이다. 넣는다면 본인 사연은 기본 비활성, 타인 사연은 링크만 — 본문 미리보기 없이 |

### 7.2 · 되돌리기가 비싼 것 — H-1·H-2 검증 전에는 넣지 않는다

| 무엇 | 왜 비싼가 |
| --- | --- |
| 의사 후기·평점 | 데이터가 쌓인다. 나중에 없애면 **사용자와의 약속을 깨는 일**이 된다. 「규제 때문에 없앴습니다」는 배신으로 읽힌다 |
| 결제·구독 | D-4. 환불·정산 이력이 남는다 |
| 비급여과 유입 | `05-decisions.md` H-2가 이미 적어 뒀다 — **「초기 유입이 급해 비급여과를 먼저 받으면 되돌릴 수 없다」** |

**「우선 넣고 나중에 뺀다」는 §7.1에는 맞고 §7.2에는 맞지 않는다.** 기준은 취향이 아니라 데이터가 남느냐다.

### 7.3 · 닥터나우 반례 — 재논의를 막기 위해 남긴다

같은 분야 최대 사업자가 §5 금지 목록을 거의 그대로 하고 있다. **이 기록이 없으면 「왜 우리만 없냐」가 주기적으로 다시 열린다.**

RN 번들에서 확인된 정렬 키:

```
DOCTOR_SORT_KEY = {
  DEFAULT:        {id:6, name:'기본순',     toast:'별점, 응답시간 등을 고려한 추천 순으로 정렬했어요.'},
  REVIEW_AVERAGE: {id:2, name:'별점높은순'},
  REVIEW_COUNT:   {id:1, name:'후기많은순'},
  PRICE:          {id:5, name:'진료비순'},
  DISTANCE:       {id:4},
  NEAREST_BOOKING:{id:0},
}
```

| 닥터나우 6.4.0 | 확인 근거 (번들 문자열) | MediVU가 금지하는 조항 |
| --- | --- | --- |
| **기본 정렬이 「별점·응답시간 고려한 추천 순」** | 위 `DEFAULT` | C-2 · IA-3 |
| 별점높은순 · 후기많은순 정렬 | 위 | C-2 |
| **진료비순 · 비급여진료비순 정렬** | `'비급여진료비순'` | C-2 · C-3 |
| 의사 후기·별점 작성 | `DiagnosisReviewScreen` · `'후기 작성'` | C-3 |
| 진료비 노출 | `'진료비와 후기를 보고 의사 선생님을 선택해 보세요'` | C-3 |
| 후기 작성 인센티브 | `'후기 작성하고 포인트 받아가세요!'` | C-3 |
| 의사 카톡 공유 | `'{의사} 선생님을 추천하고 싶어요'` | C-2 |

방어 장치도 하나 있다 — `'결제되지 않은 진료는 후기를 작성할 수 없습니다'`. **진료 완료자만 후기를 쓴다.** 후기를 언젠가 연다면 이 조건은 최소선이다.

**그럼에도 지금 열지 않는 이유**

1. **C-3은 금지 조항의 인용이 아니다.** `05-decisions.md:294` 원문은 「제57조3항의 심의 예외 항목으로만 구성한다. **그러면 설령 광고로 평가되어도 심의 예외로 편입된다**」이다. 후기를 넣는 것과 법이 금지하는 것은 다른 문제이고, **넣으면 안전지대 밖으로 나간다**가 정확한 진술이다. 닥터나우는 밖에서 리스크를 지고 있는 것이지 안이 넓다는 증거가 아니다.
2. **「하고 있다」는 「해도 된다」의 근거가 아니다.** 규모·법무 여력이 다르다.
3. **문서가 이 균형점을 이미 예언했다.** H-2 — 「홍보 ROI가 높은 곳은 비급여과라서, 내버려 두면 원하지 않는 칸이 먼저 찬다」. 닥터나우의 `PRICE: '비급여진료비순'`이 그 도착점이다. 우연이 아니라 **후기·평점·가격을 넣으면 도달하는 곳**이다.

**다시 여는 조건:** H-1·H-2가 시제품에서 살아남고, 후기 없이 의사 선택이 실제로 막힌다는 증거가 나왔을 때. 그때 `05-decisions.md`의 C-3부터 고친다.

### 7.4 · 세무통에서 가져올 구조 3개

| 무엇 | 세무통 구현 | MediVU에 옮길 때 |
| --- | --- | --- |
| **답변에 답변자 신원을 조인해 내려준다** | `postComments`에 `partnerName` `partnerOfficeName` `partnerQualification` `partnerAddress` `partnerAvatar`가 함께 온다. 답변 카드를 그리려고 별도 조회를 안 한다 | **C-3 허용 필드와 정확히 겹친다** — 의료기관 명칭·소재지·성명·면허종류. 평점·가격 필드를 만들지 않으면 구조가 곧 규제 준수가 된다 |
| **답변에서 프로필로 갈 때 출처를 남긴다** | `/experts/:id?fromAnswer=true` | §5의 「답변과 예약의 한 단계 경유」가 **실제로 지켜지는지 증명할 수단**이다. 유입 경로 없이는 감사도 못 한다 |
| **웹뷰 브리지를 최소로 묶는다** | 핸들러가 `apple sign in` · `get platform FCM token` **둘뿐**. 나머지는 전부 웹. 앱 심사 없이 배포한다 | 나중에 웹앱을 앱으로 감쌀 때 쓸 경계선. **단 MediVU는 `/visit/:roomId`가 카메라·마이크를 쓴다.** 세무통 응답 헤더는 `permissions-policy: camera=(), microphone=(), geolocation=()`로 전부 막혀 있다 — 여기서 갈라지므로 진료방만 예외를 뚫는 설계가 별도로 필요하다 |

**반대로 가져오지 않는 것** — 세무통 질문답변은 **1왕복이다.** 표본 60글 75답변에서 대댓글 0건, 질문자 재질문 0건. 스키마에 `postCommentId`가 있는데도 열지 않았다. MediVU는 **비공개 덧붙임 3왕복**(D-6 · Q-5)을 이미 열기로 정했다. 이 점에서는 MediVU가 뒤에 있는 게 아니라 앞에 있다.
