# 30 · 기능 명세 (화면 설계서)

> **이 문서가 병렬 개발의 계약서다.** 화면을 보지 않고도 구현할 수 있어야 한다.
> 화면 *사이*의 흐름은 `20-user-flows.md`, 위치와 계층은 `15-information-architecture.md`, 테이블은 `40-data-model.md`.
> 상위 결정과 제약은 `05-decisions.md`가 정본이다. 충돌하면 그쪽이 맞다.
> 마지막 대조: 2026-08-27 · 대상 커밋 `f018a58`

## 이 개정에서 바뀐 것

2026-08-19판은 화면의 **골격**만 있었다 — 목적 한 줄, 인수 조건 몇 개, 안 하는 것. 그 사이 `05-decisions.md`가 제품의 축을 바꿨고(D-1·D-5·D-6·D-8), `15-information-architecture.md`가 탭을 재편했다(Q-1~Q-4). 골격만으로는 그 결정들이 화면 어디에 앉는지 알 수 없다.

이번 판은 화면마다 **다섯 상태 · 동작 · 실제 문구 · 제약 · 금지**를 적는다. 그리고 화면마다 **왜 이렇게 생겼나**를 적는다.

**레이아웃이 아니라 근거를 적는다.** 화면 구성(HOW)이 아니라 그 선택의 이유(WHY)를 남긴다. 단순함은 결과이지 원인이 아니고, 도메인이 다르면 심리도 다르다. 금융 앱 사용자는 빨리 끝내고 싶어 하지만 **우리 사용자는 아프고 불안하다**(P-1).

**근거를 못 적는 화면은 아직 설계된 게 아니다.** 그런 화면은 목록에 남기고 「근거 미정」이라고 쓴다. 그럴듯한 이유를 지어내지 않는다. 이번 판에서 근거 미정으로 남은 화면은 셋이다 — §근거 미정.

## 읽는 법

각 화면은 아래 항목을 갖는다. 비우지 않는다. 해당이 없으면 **「해당 없음」이라고 적는다** — 빈 칸은 "아직 안 정했다"와 구별되지 않는다.

| 항목 | 무엇을 적나 |
| --- | --- |
| **구현 상태** | `있음` · `변경` · `신설(미구현)` · `부분 구현`. 코드에 없는 것을 있는 것처럼 적지 않는다 |
| **누구의 무엇을 해결하나** | 페르소나 ID(P1·P2)와 `10-personas.md`의 실패 조건. 못 적으면 이 화면은 만들지 않는다 |
| **왜 이렇게 생겼나** | 이 배치를 택한 우리 도메인의 이유 |
| **다섯 상태** | 비어 있음 · 불러오는 중 · 정상 · 오류 · 권한 없음 |
| **동작** | 누를 수 있는 것과 각각의 결과. 되돌릴 수 없는 것은 ⚠︎ 로 표시 |
| **문구** | 화면에 실제로 나가는 한국어. 자리표시자 금지 |
| **제약** | 입력 칸 수 · 한 화면의 목적 수 · 첫 피드백까지의 시간 |
| **정렬** | 무엇이 위에 오나. **그 기준이 화면에 공개되나** |
| **C-2 판정** | 의사·의료기관이 보이는 화면에만. 선택 유도인가 아닌가 |
| **금지** | 이 화면에 두면 안 되는 것과 근거 ID(C-1~C-5) |

**「비어 있음」을 특히 채운다.** 무료 커뮤니티는 초기에 사연도 답변도 없다. 빈 화면이 곧 첫인상이고, 그 화면이 "고장 난 앱"으로 읽히면 H-1을 재기도 전에 사람이 나간다.

## 공통 계약

화면마다 반복하지 않는다. 아래는 **모든 화면에 적용된다.**

### 셸

- 헤더·하단탭을 **숨기는** 화면: `/onboarding` `/ask` `/expert` `/me/*`(단 `/me` 본문은 보임) `/doctor/me/*` `/visit/*` `/doctor/visit/*`. 판정은 `App.tsx:107-113`
- 환자 하단탭 5개(목표): `홈 · 내 소식 · Q · 진료 · MY`. 중앙 `Q`가 `/ask`를 연다
- 의사 하단탭 5개: `홈 · 받은 질문 · 사연 · 진료 · MY`
- 768px 이상에서 `웹 보기 · 앱 미리보기` 전환(`PreviewToolbar`). PWA에서는 뜨지 않는다
- 모르는 경로는 `/home`으로 보낸다

### 오류는 반드시 화면에 보인다

`AppNotice`(`App.tsx:69-77`)는 헤더 **밖**에 있다. 헤더를 감추는 화면에서 등록이 실패해도 아무 일 없었던 것처럼 보이면 안 되기 때문이다. `role="status"` `aria-live="polite"`.

실패 문구는 데이터베이스 원문이 아니라 **무엇을 하면 되는지**를 적는다. 공통형은 하나다 (`CommunityContext.tsx:209-212`):

> `{무엇을}지 못했습니다. 잠시 뒤 다시 시도해 주세요. 적은 내용은 그대로 있습니다.`

「적은 내용은 그대로 있습니다」를 지우지 않는다. 아픈 사람이 길게 쓴 글을 다시 써야 하는지 모르는 것이 실패 그 자체보다 나쁘다.

### 「불러오는 중」의 기본형

라이브 모드에서 스냅샷을 아직 못 읽었을 때다 (`CommunityContext.live === null`). **모르는 것을 없는 것으로 바꾸지 않는다** — 빈 상태를 먼저 그리면 데이터가 늦게 도착했을 때 사용자는 이미 "아무것도 없다"를 본 뒤다.

- 목록 화면은 골격(스켈레톤) 3줄을 그린다. 「없어요」를 먼저 쓰지 않는다
- 첫 피드백은 **200ms 안**. 그 안에 응답이 오면 골격을 그리지 않는다(깜빡임이 더 나쁘다)
- 로딩 컨테이너에 `aria-busy="true"`를 단다. **현재 코드에 `aria-busy`는 0회다**(`50-nonfunctional.md` §접근성) — 미구현

### 시간

화면은 실제 시계(`appClock`)를 쓰고 픽스처만 기준일을 유지한다. 시간은 의료 화면에서 가장 먼저 믿는 값이라 여기가 틀리면 나머지를 다 의심하게 된다. `src/domain/`과 `src/data/`에 무인자 `Date.now()`/`new Date()`를 두지 않는다.

### 동의 문구는 실제로 일어나는 일과 같아야 한다

`00-product-definition.md` 원칙 6. **서버로 보내면서 브라우저에만 둔다고 적는 것은 오타가 아니라 동의를 잘못 받은 것이다.** 문구를 쓸 때 코드에서 실제 동작을 확인한다. 현재 확인된 사실은 이렇다.

| 데이터 | 실제로 어디로 가나 | 근거 |
| --- | --- | --- |
| 사연·답변·공감·덧붙임·예약·진료 신청 | **서버(Supabase)** | `liveRepository.ts` |
| 증상 원문 | **모델 제공자** (Edge Function 경유) | `classifyTransport.ts` |
| 사전 확인 8개 체크 (지역·질환 예외 포함) | **기기 안에만** | `localStore` |
| 주소·결제수단·알림·개인정보 설정 | **기기 안에만** | `PatientSettingsContext` |
| 화상 통화 음성 | **브라우저 제조사 서버** (내장 받아쓰기) | `useSpeechTranscript.ts` |

라이브 모드 여부로 문구가 갈리는 화면(`/ask` `/booking`)은 `isLiveMode`로 분기한다. 데모 모드에서 「서버에 저장했다」고 쓰지 않는다.

### 화면이 판정하지 않는다

화면은 도메인 출력을 렌더링만 한다. 판정은 `src/domain/`에 있고 React·라우터·픽스처를 import 하지 않는다. **새 판정 로직을 화면에 쓰고 있다면 잘못 들어간 것이다.**

### 규칙은 데이터에 두고 `asOf`를 단다

법령·운영 기준이 바뀌면 `src/data/rules/*`만 고친다. 판정 코드는 건드리지 않는다(원칙 7). 화면은 적용한 규칙셋의 **이름과 기준일을 함께 표시한다** — 이미 `/ask` `/map` `/me/precheck` `/stories`가 그렇게 하고 있다.

### 이름은 한 자리에서 만든다

진료과 한국어 이름은 `specialtyLabels` 한 곳에서만. 화면마다 들고 있으면 한 곳을 빠뜨리고, 실제로 그렇게 해서 `otolaryngology`가 그대로 환자에게 나갔다.

### 「찾지 못했습니다」에서 돌아가는 곳

세 화면(`/questions/:id` · `/doctors/:doctorId` · `/booking/:doctorId`)이 대상을 못 찾았을 때 같은 버튼을 쓴다. **현재 문구는 `게시판으로`이고 목적지는 `/board`다** — `/board` → `/stories` → (흡수 후) `/home`으로 리다이렉트가 두 번 걸린다.

**목표: 문구는 `사연 목록으로`, 목적지는 `/home` 한 번.** 못 찾은 사람을 리다이렉트 두 번에 태우지 않는다.

### 「추천」이라는 말

**화면에 등장하면 실패다.** 「추천」 「당신에게 맞는」 「인기」 「베스트」 「엄선」 — 카피에도, `aria-label`에도, 개발자 주석에도 쓰지 않는다. C-2는 대가 여부와 무관하게 **선택 유도** 자체를 금지한다. 문장 하나가 같은 화면의 적법·위법을 가른다.

### 답변과 예약의 한 단계 경유

사연 상세에서 답변을 읽고 그 의사에게 가려면 **`의사 프로필`을 반드시 한 번 거친다.**

```
/questions/:id 의 답변 카드  →  /doctors/:doctorId  →  /booking/:doctorId
                                                     →  비대면 진료 신청
```

**이 한 단계는 마찰이 아니라 분리의 증거다. 없애지 않는다.** 답변 본문 안에 예약 버튼을 두면 답변이 곧 영업 도구가 되고, 그때 답변은 의료광고가 된다. 답변 카드에서 프로필로 가는 링크는 **의사 이름과 초상**뿐이며(`AnswerCard.tsx:21-36`), 「예약하기」 「진료 보기」 같은 행동 유도 문구를 넣지 않는다.

## Q-5 · 비공개 덧붙임의 수치와 금지 표현 — **이 문서에서 정함**

`05-decisions.md` D-6은 구조 강제 6항목을 정하면서 항목 3(왕복 횟수·길이 상한)과 항목 5(금지 표현)의 **수치를 비워 뒀다.** 여기서 정한다.

**정한 값은 전부 `src/data/rules/privateThreadRules.ts`에 `asOf`와 함께 둔다** (원칙 7). 스키마나 판정 코드에 상수로 박지 않는다. 경계의 위치는 유권해석 대상이라 움직인다 — 국민신문고 회신이 오면 이 파일만 고친다.

```ts
// src/data/rules/privateThreadRules.ts — 신설 (미구현)
export const privateThreadRuleSet: PrivateThreadRuleSet = {
  name: '비공개 덧붙임 경계 시연 규칙셋',
  source: '의료법 제34조(원격의료) · 제27조3항 · 제34조의9 · 개인정보보호법 제23조',
  asOf: '2026-08-27',
  limits: { maxRounds: 3, patientMaxChars: 500, doctorMaxChars: 400 },
  bannedPatterns: [ /* 아래 표 */ ],
}
```

### 1. 왕복 횟수 상한 — **3왕복** (환자 3회 · 의사 3회)

**한 왕복 = 환자 발화 1 + 의사 회신 1.** 환자가 먼저 열고, 마지막 발화권도 의사에게 간다. 최대 6개의 메시지.

**왜 3인가.** 막으려는 것은 「사실상의 진료로 자라는 것」이다. 무엇이 진료로 자라는 순간인지를 보고 자른다.

| 왕복 | 무슨 일이 일어나나 | 판정 |
| --- | --- | --- |
| 1 | 환자가 공개 답변에서 못 물은 것 하나를 묻고 의사가 답한다 | 공개 답변의 연장 |
| 2 | 그 회신에 대한 되물음. 「그럼 언제까지 기다려도 되나요」 | 아직 일반 정보 |
| 3 | **닫는 왕복.** 의사의 마지막 회신은 진료 전환 안내를 포함한다 | 경계 |
| 4 이상 | 의사가 **되묻기 시작한다** — 「그 약은 며칠째 드셨나요」 | **문진이다. 여기가 진료다** |

4회차에서 방향이 뒤집힌다. 1~3은 환자가 묻고 의사가 답하지만, 그 뒤부터는 의사가 정보를 모아 좁혀 간다. **정보를 모아 좁히는 행위가 진료의 정의**이고, 그것이 비대면으로 일어나면 제34조다. 그래서 방향이 뒤집히기 직전에 자른다.

1왕복은 너무 짧다 — 되물을 자리가 없으면 환자는 답을 못 얻고, 이 기능은 있으나 마나가 되며, 결국 다른 사연을 새로 쓴다(같은 대화가 공개 게시판에 흩어질 뿐이다). 5왕복은 위 표의 4를 두 번 지난다.

**상한은 감추지 않는다.** 열자마자 `남은 왕복 3회`가 보인다. D-8의 답변 상한과 같은 이유다 — 언제 끝나는지 모르면 희소성이 아니라 그냥 막힘이다.

### 2. 1회 길이 상한 — 환자 **500자** · 의사 **400자**

| 대상 | 상한 | 왜 |
| --- | --- | --- |
| 환자 1회 | **500자** | 이미 올린 사연을 보충하는 자리이지 새 사연을 쓰는 자리가 아니다. 새 병력을 쓸 만큼은 못 되고, 한 가지를 맥락과 함께 묻기에는 충분하다. 부족하면 그건 새 사연이다 |
| 의사 1회 | **400자** | 400자에는 관찰할 것과 진료 시점을 적을 수 있지만 **진료 계획서를 적을 수는 없다.** 회신이 길어질수록 「불특정 다수를 향한 일반 정보」라는 방어가 약해진다 |
| 고정 고지 | **상한에 포함하지 않는다** | 의사가 지울 수 없는 글이 의사의 글자 수를 잡아먹으면 고지가 벌칙이 된다. 그러면 고지를 짧게 만들자는 압력이 생긴다 |

의사 쪽이 더 짧은 것은 의도한 비대칭이다. 위법의 주체는 환자가 아니라 의료인이고, 양벌규정(제91조)이 향하는 곳도 우리다.

**세는 법** — 공백 포함, 자모가 아니라 문자 수. 남은 글자 수를 입력 칸 아래 상시 표시하고, 넘으면 **더 입력되지 않는다**(잘라내지 않는다 — 다 쓰고 나서 뒤가 사라지면 그건 데이터 손실이다).

### 3. 처방·진단·검사 지시로 읽히는 표현

**적용 대상은 의사 회신뿐이다.** 환자 발화는 걸지 않는다 — 환자가 자기가 먹는 약 이름을 적는 것을 막으면 문진이 무너지고, 애초에 처방·진단의 주체가 아니다.

패턴은 넷으로 나눈다. **진단명 사전을 만들지 않는다** — 병명은 끝이 없어서 사전은 반드시 샌다. 대신 **단정 어미와 지시 어미**를 잡는다. 진단명을 말했는지가 아니라 **단정했는지**가 경계다.

| ID | 무엇을 잡나 | 패턴 (예시이며 정본은 규칙 파일) | 근거 |
| --- | --- | --- | --- |
| **PT-1** | 처방·투약 지시 | `처방` `처방전` `복용하세요` `드세요`(약 이름과 같은 문장) `1일 n회` `n정` `nmg` `식후 30분` `증량` `감량` `끊으세요` | C-4 · 제34조 |
| **PT-2** | 약품명 | **`medicationRules.ts`의 성분명·상품명을 그대로 재사용한다.** 새 목록을 만들지 않는다 | C-4 |
| **PT-3** | 진단 단정 | `확진` `진단명은` `진단됩니다` · `{2자 이상}(염\|증\|암\|병)(입니다\|이에요\|예요\|이네요\|입니다만)` · `n% 확률` `중증도` `n기입니다` | **C-5** |
| **PT-4** | 검사·시술 지시 | `{검사명}(받으세요\|하세요\|찍으세요\|받아보세요\|예약하세요)` — 검사명은 `CT` `MRI` `엑스레이` `내시경` `초음파` `조직검사` `피검사` `혈액검사` | C-4 · C-5 |
| **PT-5** | 의료기관 유치 | `우리 병원` `저희 병원` `저희 의원` `내원하세요` `오세요`(의료기관명과 같은 문장) · **의료기관명 직접 언급** | **C-2 · C-3** |

**PT-4가 지시형 어미까지 묶는 이유** — 「내시경으로 봐야 하는 경우가 많습니다」는 일반 의학정보이고, 「내시경 받으세요」는 검사 지시다. 검사명 자체를 막으면 의사가 아무 설명도 못 하고, 그러면 답변이 무의미해진다. **막는 것은 지시이지 지식이 아니다.**

**PT-5는 공개 답변에도 적용한다.** C-3이 이미 요구하고 있다 — 「답변 본문 안의 병원명 언급은 필터로 막고, 필터링 로그를 보관한다」.

### 4. 걸렸을 때의 동작

**막는다. 경고만 하고 보내지 않는다.** 화면이 아무것도 막지 않으면서 막는다고 적는 것은 원칙 6 위반이고, D-6이 「문구가 아니라 구조로 강제한다」고 정한 자리가 바로 여기다.

1. **전송이 되지 않는다.** 「보내기」가 비활성이 아니라, 눌렀을 때 걸린 자리를 보여 준다(비활성 버튼은 이유를 말하지 못한다)
2. **걸린 조각을 본문에서 그 자리에 표시한다.** 어디가 걸렸는지 모르면 고칠 수 없다
3. **패턴 종류별로 다른 문장을 낸다.** 「부적절한 표현입니다」 같은 뭉뚱그린 문구를 쓰지 않는다 — 무엇을 고쳐야 하는지 알 수 없다
4. **막힌 곳에서 나갈 길을 함께 준다.** 「진료가 필요합니다」 전환 버튼(D-6 항목 6)이 같은 자리에 있다. 처방이 필요해서 막힌 것이면 필요한 것은 문장 수정이 아니라 진료다
5. **기록을 남긴다** — 아래

양벌규정(제91조)의 「상당한 주의·감독」을 입증하는 데 필요한 것은 **우리가 걸렀다는 사실**이지 환자의 증상 원문이 아니다.

### `/home` · 홈 = 사연 피드 + 진행 상태 스트립 — **변경 · 우선**

**구현 상태** — **변경(미구현).** 현재 `/home`은 `resolveNextStep` 대시보드이고 사연 피드는 `/stories`에 있다. D-5가 둘을 뒤집었다.

**누구의 무엇을 해결하나** — P1, 두 상태 모두.

- **볼 의사를 모르는 P1** — 「어느 과인지 모르겠다」로 앱을 연다. 홈이 곧 사연 피드여야 남의 사연에서 자기 증상을 발견하고 쓸 마음이 생긴다
- **볼 의사를 아는 P1**(두 번째 방문부터) — 실패 조건은 이것이다: *「신청 버튼이 회색으로 변하는 것이 전부면, 자기 요청이 살아 있는지 사라졌는지 알 수 없다. 아픈 상태에서 그 모름은 그냥 불안이다.」* 진행 상태 스트립이 이 실패를 막는다

**왜 이렇게 생겼나**

D-5가 홈을 사연 피드로 정하면서 **갈 곳을 아는 환자에게 한 단계가 늘었다.** 이걸 홈을 상태에 따라 바꿔서 풀지 않는다 — **홈이 사람마다 다르면 설명도 테스트도 어려워진다.** 대신 피드 위에 얇은 스트립 하나를 고정한다. 스트립은 자리를 늘리는 대신 **결정 횟수를 늘리지 않는다**(진행 중인 건이 없으면 아예 없고, 있으면 가장 급한 하나만 뜬다). 이것이 P-1의 「줄이는 것/늘리는 것」 표를 이 화면에 적용한 모습이다.

**내 사연 탭을 여기에 두지 않는다.** 현재 `/stories`는 `전체 · HOT · 내 사연` 셋을 갖는데, 「내 사연」은 `/news`와 같은 것을 가리킨다. 한 화면의 목적 수를 줄이는 쪽(P-1)을 택해 **홈은 남의 사연을 읽는 자리, 내 소식은 내 것을 보는 자리**로 가른다.

**왜 이렇게 생겼나**

- **없어도 글이 올라가는 것은 접는다. 지우지는 않는다.** 스물여섯 칸을 다 보여 주면 거기서 그만두지만, 적어 준 만큼 답변이 정확해지는 것도 사실이다. 그래서 `<details>` 하나로 접는다 — 요약줄에 `더 적으면 답변이 정확해져요`를 두어 **접힌 것이 안 중요한 것이 아님**을 밝힌다
- **고칠 수 없다는 규칙은 시작 전에 알린다.** 다 쓰고 나서 알면 늦고, 되돌리려면 처음부터 다시 써야 한다. 1단계 맨 위와 확인 단계 두 곳에 같은 경고를 둔다
- **민감한 범주는 추론으로 열지 않는다.** 문항 은행은 추론된 부위에 해당하는 것만 열고, 여성 건강·마음처럼 민감한 범주는 환자가 **직접 고를 때만** 연다(원칙 5). 분류기는 또 틀리고, 틀렸을 때 무엇이 새는지로 경계를 정한다
- **부위 체크박스는 진료과 키워드로만 확장한다.** 응급 신호 키워드는 하나도 넣지 않는다(`intakeRules.ts`) — 체크박스 한 번으로 119 안내가 뜨면 그건 증상 정리 양식이 아니라 선별검사 도구다
- **셸을 숨긴다.** 3단계 작성 중 이탈이 곧 미완성 사연이다

### `/questions/:questionId` · 사연 상세 — **변경 · 우선**

**구현 상태** — **변경.** 공개 사연·답변 목록·공개 덧붙임·삭제는 **있음**. **비공개 덧붙임(D-6)은 미구현** — 현재 `question_notes`는 글쓴이가 쓰고 **모두가 읽는** 공개 덧붙임이다. 둘은 다른 것이며 화면에서 섞지 않는다.

**누구의 무엇을 해결하나** — P1. *「답변 하나만 크게 뜨거나 "당신에게 맞는 의사"가 뜨면, 고른 것이 자기가 아니게 된다. 그 순간 제34조의9 문제이기도 하다」* 이 화면이 지키는 것은 **고르는 주체가 환자라는 사실**이다. 그리고 P1은 「모인 답변을 다 보고 스스로 고른다」로 앱을 쓴다.

**왜 이렇게 생겼나**

- **답변을 전부, 같은 크기로 늘어놓는다.** 하나를 크게 하거나 위로 올리는 순간 그건 우리가 고른 것이 된다(C-2). 「베스트 답변」·「채택」이 없는 이유다
- **사연은 고칠 수 없고 덧붙일 수만 있다.** 지나간 증상 설명이 조용히 바뀌면 그 위에 달린 답변이 무엇을 보고 쓴 것인지 알 수 없어진다. 삭제는 되지만 답변과 덧붙임이 함께 사라진다
- **진료과 안내와 응급 안내는 글쓴이에게만 보인다.** 남의 글을 읽는 사람에게 「어느 과로 가면 좋을까요」는 자기 얘기가 아니다. 다른 사람에게는 작성자 줄의 진료과 칩으로 충분하다
- **비공개 덧붙임이 여기 붙는 이유** — 답변을 읽은 그 자리에서 열려야 한다. 별도 화면으로 빼면 환자는 「무엇을 보고 묻는지」를 잃고, 의사는 자기 공개 답변을 떠난 채로 회신하게 된다. 공개 답변이 문맥으로 붙어 있는 것 자체가 「일반 정보의 연장」이라는 방어의 일부다

### `/doctors/:doctorId` · 의사 프로필 — **변경 · 우선**

**구현 상태** — **변경.** 화면은 있으나 **프로필 필드가 C-3 밖이다.** `bio`·`consultStyle`·`career`가 자유 서술이고, 제57조3항의 심의 예외 항목이 아니다.

**누구의 무엇을 해결하나** — P1. 답변을 읽고 「이 사람에게 가도 될까」를 판단하는 자리다. 실패 조건은 두 방향이다 — 정보가 없으면 못 고르고, 홍보성 정보가 있으면 고른 것이 자기가 아니게 된다.

**왜 이렇게 생겼나**

- **두 진입로가 합류하는 유일한 지점이다**(`20-user-flows.md`). 사연에서 온 P1도, 지도·재진에서 온 P1도 여기를 지난다. **예약과 비대면 신청은 여기서만 시작한다** — 시작점이 하나여야 「답변과 예약의 분리」가 구조로 성립한다
- **필드를 늘리지 않고 줄인다.** 제57조3항의 심의 예외 항목으로만 구성하면, 설령 이 화면이 의료광고로 평가되더라도 심의 예외로 편입된다. 프로필을 풍성하게 만드는 것이 이 화면에서는 **위험을 늘리는 일**이다
- **막힌 이유를 감추지 않는다.** 비대면이 안 되면 버튼을 숨기는 대신 비활성으로 두고 사유를 적는다 — **없는 것과 못 하는 것은 다르다**

### `/news` · 내 소식 — **변경(탭 승격) · 우선**

**구현 상태** — **변경.** 화면은 있고 헤더 종 아이콘으로 들어간다. 탭 승격과 「내 사연」 흡수가 미구현.

**누구의 무엇을 해결하나** — P1의 네 번째 동작 — *「답이 왔는지 확인하러 다시 들어온다」*. 그리고 IA-2의 구체 요구: **내 요청이 지금 어디까지 왔는지는 어느 화면에서든 두 번 안에 닿아야 한다.**

**왜 이렇게 생겼나**

**무료 커뮤니티에서 재방문의 이유는 하나다 — 내 사연에 답이 달렸는가.** 그 보상을 헤더 종 아이콘에 두면 앱의 심장이 부속으로 밀린다. D-1이 Q&A를 축으로 정한 이상 여기는 탭이어야 한다.

**낱개로 늘어놓는다.** 홈은 사연 하나를 한 줄로 묶지만(`groupMyActivity`) 여기는 묶지 않는다(`buildMyActivity`). 홈에서 알고 싶은 것은 「몇 개 왔나」이고, 여기서 알고 싶은 것은 「누가 뭐라고 했나」다. 같은 데이터를 다른 굵기로 쓴다.

### `/care` · 진료 — 주변 · 재진 · 예정 — **신설(미구현) · 우선**

**구현 상태** — **신설.** 라우트가 없다. 지도는 `/map`에, 예정된 예약은 `/me/appointments`에 흩어져 있고 **재진(내가 진료봤던 곳)은 어디에도 없다.**

**누구의 무엇을 해결하나** — **P1의 두 번째 상태.** *「두 번째부터는 상태가 다르다 — 볼 의사를 이미 안다. 같은 사람이지 다른 페르소나가 아니다.」* 이 상태의 실패는 **게시판을 한 번 더 지나야 하는 것**이고, D-5가 그 비용을 만들었으므로 이 탭이 갚는다.

**왜 이렇게 생겼나**

- **IA-1의 두 번째 진입로 전체가 여기 들어간다.** 지도(주변)와 진료 이력(재진)은 「볼 의사를 아는 환자」라는 **같은 상태**를 다룬다. 별개 탭 두 개로 쪼개면 5개 자리에 안 들어가고, 사용자에게도 같은 일이 두 곳에 있는 것처럼 보인다
- **예정된 예약을 여기 두는 이유**(Q-2) — 예약을 잡은 사람은 이미 볼 의사를 아는 사람이다. MY(설정)에 두면 「내 진행 중인 일」이 설정 화면 안에 숨는다
- **두 출처를 섞지 않는다**(Q-4) — 검증되지 않은 데이터가 검증된 것처럼 보이면, 그건 P1의 실패 조건(「화면이 자기 말을 대신 만들어 낸 것이 된다」)과 같은 종류의 배신이다. 뱃지로 구분하지 않고 **섹션을 나눈다.** 뱃지는 스크롤하면서 놓친다

- 화면 안내: `예정된 진료와 다니던 곳, 그리고 주변 의원을 한곳에서 봅니다.`
- 3구역 안내: `내 지역을 기준으로 초진 비대면 진료가 열리는 곳을 함께 표시합니다. 재진은 지역 제한을 받지 않습니다.`
- 막힌 사유(그대로): `비대면 진료를 운영하지 않는 의료기관입니다.` / `병원급은 희귀질환 등 예외 사유에만 비대면이 열립니다.` / `초진 비대면은 같은 지역만 가능합니다. 내 지역 {지역}, 의료기관 {지역}.` / `이번 달 비대면 진료 비율 상한을 넘겨 접수가 어렵습니다.`
- 하단 고지: `실제 지도와 위치 정보가 아닌 가상 약도입니다. 판정 기준 {규칙셋 이름} · 기준일 {asOf}`
- **정렬 공개(신설):** `내 지역을 먼저, 그 다음 진료 가능 여부, 같으면 이름 가나다순으로 늘어놓습니다. 노출 순서를 팔지 않습니다.`

**제약** — 입력 칸: 기준 지역 1개 + 직접 등록 시 2개 · 목적 3개(진행 확인 · 재진 · 탐색)이며 **위에서 아래로 급한 순이라 한 번에 하나만 읽으면 된다** · 첫 피드백 200ms.

**정렬**

| 구역 | 기준 | 공개 |
| --- | --- | --- |
| 1 | 진료방 열림 > 예약 예정 > 신청 대기, 같으면 최신순 | 적는다 |
| 2 | 마지막 진료일 내림차순. 두 출처는 섞지 않으므로 서로 비교되지 않는다 | 적는다 |
| 3 | ① 내 지역 ② 초진 비대면 가능 ③ 이름 가나다순 (`clinicFinder.ts:66-72`) | **적는다 — 현재 미구현** |

**C-2 판정 — 밖, 단 3구역이 가장 아슬아슬하다.**

제34조의9의 예외는 **환자 요청에 따라 지역 내 기관명과 소재지를 종합적으로 안내하는 것** 하나다. 3구역은 그 예외에 정확히 앉아 있어야 한다.

| 판정 근거 | |
| --- | --- |
| 환자가 지역을 **직접 고른다** | 「환자 요청에 따라」 |

**금지**

### `/booking/:doctorId` · 대면 예약 3단계

**구현 상태** — 있음

**누구의 무엇을 해결하나** — P1(볼 의사를 아는 상태). 실패는 「예약한 줄 알았는데 안 되어 있는 것」이다. 앱이 하는 일은 희망 시간 전달까지이고 확정은 병원이 하는데, 화면이 「예약 완료」라고 쓰면 환자는 병원에 안 간다.

**왜 이렇게 생겼나**

- **날짜와 시간을 한 화면에 두지 않는다.** 2주치 날짜 14개 × 시간 칸이면 예순 개를 넘고, 그러면 어디까지 했는지 사라진다. 단계를 나눈 이유는 「입력 칸 수를 줄인다」(P-1)의 직접 적용이다
- **못 고르는 날을 지우지 않고 비활성으로 둔다.** 휴진과 마감을 각각 다른 글자로 적는다 — 없는 것과 못 하는 것은 다르다
- **서류를 여기서 함께 고른다.** 진료의 목적이 서류인 경우가 있다(실손 청구, 회사 제출). 진료가 끝난 뒤에 알면 다시 가야 한다
- **화면이 지어낸 id를 쓰지 않는다.** 서버가 자기 id를 만들기 때문에 화면 id로는 영영 만나지 못하고, 그러면 전달해 놓고도 전달했다는 화면이 안 뜬다. **의사·날짜·시간 셋이 진짜 열쇠**이고 서버도 그 셋으로 중복을 막는다

| 상태 | 화면 | 다음 |
| --- | --- | --- |
| 비어 있음 | 고른 날에 시간 칸이 없을 때: `이 날은 진료하지 않습니다. 다른 날을 골라 주세요.` | 날짜 단계로 |
| 불러오는 중 | 해당 없음 — 날짜·시간은 `clinicHours`에서 로컬로 계산한다. 네트워크를 타는 것은 전달 한 번뿐 | — |
| 정상 | `1 / 3 · 날짜` → `2 / 3 · 시간` → `3 / 3 · 확인` | 다음 단계 |
| 오류 | 없는 의사: `의사 정보를 찾지 못했습니다.` + 돌아가는 버튼. 전달 실패: `AppNotice` 공통형. **고른 날짜·시간·서류는 남는다** | 재시도 |
| 권한 없음 | 해당 없음 — 대면 예약은 언제나 열려 있다. 사전 확인도 필요 없다 | — |

**동작**

| 누르는 것 | 결과 |
| --- | --- |
| 날짜 칩 | 선택. 휴진·마감은 비활성 |
| 시간 칩 | 선택. 고르기 전에는 다음으로 못 간다 |
| 서류 체크 | 선택(0개 가능) |
| `희망 시간 전달` | ⚠︎ `bookings` INSERT. **취소 수단이 앱에 없다** — 취소는 병원에 전화한다 |
| `병원 예약 페이지로` | 외부 링크. 확인 단계에만 있다 |
| `이전` | 단계 뒤로 |

**문구**

- 제목: `초진 대면 진료 예약`
- 단계: `1 / 3 · 날짜` · `2 / 3 · 시간` · `3 / 3 · 확인`
- 날짜 단계: `언제 진료받으시겠어요` · 비활성 칩에 `휴진` 또는 `마감`
- 시간 단계: `{날짜} 몇 시가 좋으세요` · 시간대 구분 `새벽` `오전` `오후` `야간` · 새벽·야간 주의 `이 시간대에는 진료 가능한 의사가 적을 수 있어요.` · `점심시간 {시간}은 제외했습니다.`
- 서류: `진료 후 필요한 서류가 있나요 (선택)` · `발급은 병원이 합니다. 신청 내용에 함께 전달됩니다.`
- **전달 후:** `{날짜} {시간} 희망 시간을 전달했습니다.` + `병원이 확인해야 예약이 확정됩니다. 확정 연락은 {전화번호}에서 옵니다.`
- 하단 고지(라이브): `MediVU가 예약을 확정하지 않습니다. 희망 시간을 병원에 전달하는 시연입니다. 고른 날짜와 시간은 함께 테스트하는 서버에 저장되고 해당 의사 계정에서 볼 수 있습니다.`
- 하단 고지(데모): `…이 브라우저에만 저장되며 어디로도 전송되지 않습니다.`

**제약** — 단계당 결정 1개 · 날짜 목록 2주치 · 첫 피드백 즉시(로컬 계산) · **입력 칸 0개**(전부 고르는 것이다. 아픈 사람에게 타이핑을 시키지 않는다).

**정렬** — 날짜는 오늘부터 차례로. 시간은 시간대(새벽·오전·오후·야간) 안에서 이른 순. 정렬할 여지가 없는 축이라 별도 공개 문구를 두지 않는다.

**C-2 판정 — 밖.** 의사 한 명이 이미 정해진 상태로 들어온다. 다른 의사를 제시하지 않는다.

**금지** — 예약 「확정」 문구(앱이 확정하지 않는다) · 결제·선결제·노쇼 수수료(D-4 · C-1) · 「빠른 예약」 유료화(C-1) · 다른 의사·병원 제안(C-2) · 진료비 표시(C-3).

### `/me/precheck` · 비대면 사전 확인

**구현 상태** — 있음

**누구의 무엇을 해결하나** — P1. 실패는 「신청 버튼이 왜 안 눌리는지 모르는 것」이다. 비대면 진료는 자격 요건이 여러 개인데, 막힌 이유를 안 알려 주면 환자는 앱이 고장 났다고 생각한다.

**왜 이렇게 생겼나**

- **확정 판정이 아니라 예비 점검이다.** 최종 판단은 의료진이 한다. 화면 문구가 이 경계를 넘으면 그건 우리가 진료 대상 여부를 판정한 것이 된다
- **끝난 것과 남은 것을 낱개로 보여 준다.** 「완료/미완료」 한 덩어리로 보여 주면 무엇이 부족한지 알 수 없어 사람이 끝까지 가지 않는다. 그래서 `carePrepProgress`가 4항목으로 쪼갠다
- **기기 안에만 둔다.** 사는 지역과 질환 예외는 민감정보다. 이 데모의 DB는 해외 리전이고 의료정보를 다룰 접근통제가 없다. **그래서 화면에도 그렇게 적는다** — 원칙 6

| 상태 | 화면 | 다음 |
| --- | --- | --- |
| 비어 있음 | 첫 방문. 조건 6줄 + 폼. `비대면 사전 확인 전` | 폼 작성 |
| 불러오는 중 | 해당 없음 — `localStore`에서 즉시 읽는다 | — |
| 정상 (완료 전) | 조건 목록 + 폼 + 비활성 제출 버튼 | 제출 |
| 정상 (완료 후) | 4항목 진행 목록 + 남은 것으로 보내는 버튼 | `/me/address` 또는 `/home` |
| 오류 | `localStorage`가 막혔으면 저장이 안 된다. **화면은 통과시키되 알린다:** `이 브라우저에서는 확인 내용을 저장할 수 없습니다. 창을 닫으면 다시 입력해야 합니다.` | 계속 |
| 권한 없음 | 해당 없음 | — |

**동작** — 지역·이번 달 횟수·질환 예외 선택 · 본인 확인 체크 · 조건 확인 체크 · `사전 확인 마치기`(둘 다 체크해야 활성). 완료 후 `주소 설정하러 가기` 또는 `답변해 준 의사 찾아보기`.

**문구**

- 안내: `한 번만 확인해 두면 의사 프로필에서 비대면 진료가 가능한지 바로 보입니다.`
- 조건 6줄은 `eligibilityRuleSet.params`에서 값을 받아 그린다(숫자를 문장에 박지 않는다)
- 체크: `본인 확인을 마쳤습니다 (시연용 체크)` · `위 조건을 확인했습니다`
- 완료: `사전 확인을 마쳤습니다` → 4항목 다 채우면 `비대면 진료를 받을 수 있습니다`
- **하단 고지:** `이 확인은 이 기기에만 저장되고 서버로 보내지 않습니다. 실제 본인확인 절차가 아닙니다. 적용 규칙 {규칙셋 이름} · 기준일 {asOf}`

**제약** — 입력 칸 5개(지역·횟수·예외·체크 2) · 목적 1개 · 첫 피드백 즉시 · 셸 숨김(한 화면 한 목적).

**정렬** — 해당 없음.

**C-2 판정** — 해당 없음. 의사가 등장하지 않는다.

**금지** — 사는 지역·질환 예외를 서버로 보내는 것(원칙 6 · `50-nonfunctional.md`) · 실제 본인확인이라고 적는 것 · 확정 판정 문구 · 진단명(C-5) · 여기서 바로 특정 의사에게 신청하게 하는 것(C-2 — 신청은 프로필에서 시작한다).

### `/visit/:roomId` · 화상 진료방 (환자)

**구현 상태** — 있음. **화면 테스트가 없는 유일한 주요 화면**(도메인 테스트만 있다).

**누구의 무엇을 해결하나** — P1과 P2 둘 다. P1의 실패는 「빈 방에서 혼자 기다리는 것」이고, P2의 실패는 「통화하면서 기록까지 손으로 쓰는 것」이다.

**왜 이렇게 생겼나**

- **의사가 여는 방이다.** 환자가 먼저 들어와 기다리고 의사가 부른다. 진료를 여는 사람이 의사이기 때문이고, 그래야 환자가 빈 방에서 기다리지 않는다
- **각자 자기 마이크만 받아 적는다.** 상대 목소리를 내가 받아 적으면 마이크 품질에 따라 엉뚱한 말이 기록으로 남는다
- **통화용 키워드 규칙을 따로 만들지 않는다.** 사연 분류와 **같은 규칙셋**을 쓴다. 두 개를 만들면 기준이 갈라지고 어느 쪽이 맞는지 아무도 모르게 된다
- **키워드와 기록 초안은 의사에게만 보인다.** 환자 화면에 키워드를 띄우면 그건 진단으로 읽힌다(C-5)
- **직접 연결(WebRTC)을 택한 이유** — 계정을 하나 더 만들지 않아도 되고, 다음 단계에서 프레임을 직접 암호화하려면 어차피 `PeerConnection`을 우리가 들고 있어야 한다

| 상태 | 화면 | 다음 |
| --- | --- | --- |
| 비어 있음 | 통화 기록 0줄: `받아쓰기를 켜면 오간 말이 여기에 쌓입니다.` 키워드 0개(의사): `아직 뽑을 말이 없습니다.` | 받아쓰기 시작 |
| **불러오는 중** | 자격 확인 중(라이브 모드에서 스냅샷 전): `진료방을 확인하는 중입니다…` **모르는 것을 거절로 바꾸지 않는다** | 확인 후 분기 |
| 정상 | 영상 2개 + 상태 라벨 + 통화 기록 + (의사만) 키워드·기록 초안 | — |
| **오류** | 연결 실패·마이크 문제를 **각각 다른 문장으로.** 브라우저 미지원: `이 브라우저는 받아쓰기를 지원하지 않습니다. Chrome에서 열어 주세요.` 받아쓰기가 막혀도 **손으로 한 줄 넣는 길**이 있다 | 직접 입력 |
| **권한 없음** | `이 진료방에 들어갈 수 없습니다` / `이 방은 신청한 환자와 담당 의사만 들어갈 수 있습니다. 주소를 받았더라도 당사자가 아니면 열리지 않습니다.` **서버(RLS)가 판단한다** — 내 `encounters`에 그 방이 없다는 것은 내가 당사자가 아니라는 뜻이다 | `돌아가기` |

**동의 게이트 (입장 전)**

녹음과 전사는 동의를 받고 시작한다. 동의 없이 받아 적으면 안 된다.

- `통화 내용을 글로 받아 적습니다` — `내 마이크에 들어온 말만 내 기기에서 글로 바꿔 상대에게 보냅니다.` / `영상과 음성은 두 사람의 브라우저 사이로 직접 흐릅니다.` / `받아 적은 글은 진료 기록 초안을 만드는 데 쓰입니다.`
- **실제로 일어나는 일을 그대로 적는다:** `지금은 브라우저 내장 받아쓰기를 씁니다. 이 기능은 음성을 브라우저 제조사 서버로 보냅니다. 그래서 이 데모에는 실제 증상이나 개인정보를 말하지 마세요. 실서비스에서는 기기 안에서만 도는 받아쓰기로 바꿔야 합니다.`

**동작** — `진료방 들어가기` · `통화 종료`(⚠︎ 마이크를 닫는다) · `받아쓰기 시작/멈춤` · 손으로 한 줄 `보내기` · (의사) `초안 복사`.

**끊길 때** — 통화가 끝나면 마이크를 닫는다. **종료 버튼과 연결 종료 양쪽에서.** 내가 누르지 않은 종료에서 계속 듣고 있으면, 그건 기능 문제가 아니라 사람이 모르는 채로 녹음되는 문제다.

**제약** — 입력 칸 1개(손으로 넣는 줄) · 목적 1개(통화) · 셸 숨김(실수로 나가면 상대가 혼자 남는다) · 뒤로 가기는 **나가기 확인**을 받는다(**미구현**).

**정렬** — 통화 기록은 시간순. 키워드는 나온 순서. 정렬하지 않는다.

**C-2 판정** — 해당 없음. 당사자 둘만 있는 방이다.

**한계 (실서비스 전 필수)** — TURN 없음(대칭 NAT에서 실패) · 브라우저 내장 전사가 음성을 제조사 서버로 보냄 · **시그널링 채널이 방 이름만으로 구독 가능**(`20-user-flows.md` §권한).

**금지** — 진단명을 만들지 않는다. 뽑히는 키워드는 **말에 실제로 있었던 단어**다(C-5). 환자 화면에 키워드·기록 초안을 띄우지 않는다. 통화 내용을 서버에 저장하지 않는다 — 화면에 그렇게 적혀 있으므로 실제로도 그래야 한다(원칙 6).

**데모 방(`demo-*`)** — 신청 없이 주소만으로 열린다. 하단에 그대로 적는다: `신청 없이 여는 시연용 방입니다. 주소를 아는 사람은 누구나 들어올 수 있습니다.` **실서비스에서 가장 먼저 없앨 자리다.**

**C-2 판정** — 해당 없음.

**금지** — 결제·구독 화면(D-4) · 「내게 맞는 의사 찾기」 바로가기(C-2) · 실제 카드번호·CVC(`50-nonfunctional.md`).

### MY 설정 5종 — `/me/address` `/me/payment` `/me/notifications` `/me/privacy` `/me/appointments`

**구현 상태** — 다섯 화면 모두 **있음.** `/me/appointments`만 폐지 예정(Q-2 → `/care` 흡수).

**왜 이렇게 생겼나 (다섯 화면 공통)** — 설정은 한 번 정하고 두는 것이라 **셸을 숨긴다**(한 화면 한 목적). 그리고 다섯 화면 모두 **저장 버튼이 있고, 눌렀다는 사실 자체를 남긴다** — 기본값이 있는 항목은 값만 보고는 사용자가 확인했는지 알 수 없기 때문이다(`address.savedAt`). 진행률 계산이 그 값을 쓴다.

**C-2 판정 — 해당 없음.** 다섯 화면 모두 의사·의료기관이 등장하지 않는다. 단 `/me/appointments`에는 **내가 이미 희망 시간을 전달한 의사**가 나오며, 이는 후보 목록이 아니라 내 요청의 상대다 — 다른 의사를 제시하지 않는다.

**정렬** — `/me/appointments`만 해당(최신 전달 순). 나머지 넷은 고정 순서 폼이라 정렬 대상이 없다.

**공통** — 상단에 `← MY로 돌아가기`. 저장하면 `role="status"`로 저장 문구가 뜬다. **다섯 화면 모두 값을 기기 안에만 둔다** — 화면에도 그렇게 적는다.

| 상태 | 다섯 화면 공통 |
| --- | --- |
| 비어 있음 | `/me/appointments`만 해당(아래). 나머지는 기본값이 있어 빈 상태가 없다 |
| 불러오는 중 | 해당 없음 — 전부 `localStore`에서 즉시 읽는다 |
| 정상 | 폼 + 저장 버튼 + 저장 후 상태 문구 |
| 오류 | `localStorage`가 막혔으면 `이 브라우저에서는 설정을 저장할 수 없습니다.` **폼은 계속 쓸 수 있다** |
| 권한 없음 | 해당 없음 — 내 설정이다 |

#### `/me/address` · 주소 설정

**구현 상태** — 있음

**누구의 무엇을 해결하나** — P1. `carePrepProgress`의 4번째 항목이다. **별칭 없이 지역만 골라도 채워진다** — 지역에는 기본값이 있어 값만 보고는 확인했는지 알 수 없으므로 **사용자가 저장을 눌렀는지**(`savedAt`)를 남겨 그것으로 판단한다.

**왜 이렇게 생겼나** — 지역 목록은 의료기관 지역 목록과 **같은 것**(`demoRegions`)을 쓴다. 두 벌이면 「내 지역에 병원이 없다」가 오타 때문에 생긴다.

**문구** — `지역만 고르고 저장해도 됩니다. 별칭은 여러 곳을 구분할 때만 씁니다. 주소 확인과 병원 전송은 아직 연결되지 않은 데모이니 실제 상세 주소는 적지 마세요.` · 저장 후 `주소를 저장했습니다.`

**제약** — 입력 칸 2개(지역 · 별칭, 별칭은 선택) · 목적 1개.
**금지** — 실제 상세 주소를 서버로 보내는 것 · 위치 권한 요청.

#### `/me/payment` · 결제수단 설정 — **근거 미정**

**구현 상태** — 있음 · 제거 권고

**왜 이렇게 생겼나 — 근거 미정.** 이 자리에 우리 도메인의 이유를 적을 수 없다.

**누구의 무엇을 해결하나** — **적을 수 없다.** D-4가 「무료로 출시한다. 결제 기능을 만들지 않는다」로 닫혔고, `15-information-architecture.md` §5가 「결제·구독·상단 노출 구매 화면」을 두지 않는 목록에 넣었다. **이 화면은 그 목록에 걸린다.**

**근거 미정.** 그럴듯한 이유를 지어내지 않는다. 남은 선택지는 둘이고 D-4를 고치지 않는 한 답은 정해져 있다.

| 선택지 | 판정 |
| --- | --- |
| 화면을 지운다 | D-4·IA §5와 맞는다. **권고** |
| 남긴다 | D-4를 먼저 고쳐야 한다 |

지울 때까지 지키는 것 — 실제 카드번호·CVC를 받지 않는다. 문구 그대로: `표시된 수단은 시연용이며 실제 카드 번호·CVC를 입력하거나 결제하지 않습니다.`

**금지** — 실제 결제 · 구독 · 진료비 % 수수료 · 성과 연동 과금(D-4의 영구 금지 목록).

**제약** — 입력 칸 3개(체크) · 목적 1개.

#### `/me/privacy` · 개인정보 설정

**구현 상태** — 있음

**누구의 무엇을 해결하나** — P1. 새 사연의 기본 공개 범위를 미리 정해 둔다. 매번 3단계에서 고르게 하면 결정 횟수가 는다(P-1).

**왜 이렇게 생겼나** — 기본값은 **공개**다. D-1이 공개 Q&A를 축으로 정했고, 비공개가 기본이면 게시판이 처음부터 비어 있다. 다만 바꾸는 자리를 여기 둔다.

**문구** — `모든 사용자에게 공개` / `관련 진료과 의사에게만` / `이전에 방문한 병원에게만` · `실제 동의 기록이나 서버 공개 범위에는 아직 반영되지 않는 데모입니다.`

**제약** — 입력 칸 2개 · 목적 1개.

**금지** — 「이 설정을 켜면 답변을 더 빨리 받습니다」류의 유도 · 공개 범위를 우리가 추론해서 바꾸는 것(원칙 5).

#### `/me/appointments` · 예약 내역 — **폐지 예정**

**구현 상태** — 있음 · 폐지 예정

**누구의 무엇을 해결하나** — P1(볼 의사를 아는 상태). 「예약한 줄 알았는데 안 되어 있는 것」을 막는다.

**왜 이렇게 생겼나** — 이 화면이 **설정 안에 있는 것이 잘못이다.** 예약은 설정이 아니라 진행 중인 일이고, 진행 중인 일이 설정 화면에 숨으면 IA-2(「내 요청이 어디까지 왔는지는 두 번 안에 닿아야 한다」)를 지킬 수 없다. Q-2가 `/care`로 합치기로 닫았다. **리다이렉트만 남긴다** — 기존 링크와 북마크가 살아 있어야 한다.

흡수 전까지의 명세: 비어 있음 `전달한 희망 시간이 없어요` / `사연에 답변한 의사 프로필에서 대면 진료 희망 시간을 고르면 여기에 쌓입니다.` + `내 주변 병원 보기` · `사연 둘러보기`. 정상은 `예약 확정 전` 태그 + 의료기관명 + 날짜·시간 + `{의사}에게 희망 시간을 전달했습니다.` 하단 `병원이 확인하기 전까지 예약은 확정되지 않습니다.` **정렬: 최신 전달 순.**

### `/stories` · 사연 목록 — **폐지 예정 → `/home` 리다이렉트**

**구현 상태** — 있음 · 폐지 예정

**누구의 무엇을 해결하나** — P1(볼 의사를 모르는 상태). 남의 사연에서 자기 증상을 발견하는 자리다. **`/home`이 이 역할을 그대로 가져간다.**

**왜 이렇게 생겼나** — **이 화면이 남아 있는 것이 잘못이다.** D-5가 홈을 사연 피드로 정하면서 `홈`과 `사연` 두 탭이 같은 것을 가리키게 됐다. 같은 것이 두 곳에 있으면 사용자는 둘이 다른 줄 알고 양쪽을 다 확인한다 — 그건 결정 횟수를 늘리는 일이다(P-1).

내용(전체·HOT 탭, 진료과 필터, 공감, 최신순, 규칙셋 표시)은 **`/home`으로 옮긴다.** `내 사연` 탭은 `/news`로 간다.

| 상태 | 흡수 전까지 | 흡수 후 |
| --- | --- | --- |
| 비어 있음 | `아직 올린 사연이 없어요`(내 사연 탭) / `해당하는 사연이 없어요`(그 외) | `/home`의 비어 있음 명세를 따른다 |
| 불러오는 중 | 카드 골격 3장 | 〃 |
| 정상 | 탭 3개 + 진료과 필터 + 카드 목록 | `/home`으로 리다이렉트 |
| 오류 | `AppNotice` 공통형 | 〃 |
| 권한 없음 | 해당 없음 — 공개 사연만 실린다 | 해당 없음 |

**제약** — 입력 칸 0개 · 목적 3개(읽기 · 내 것 보기 · 공감)이며 **이 셋이 많다는 것이 흡수의 이유다.** 흡수 후 `/home`은 2개, `/news`가 1개를 가져간다. 첫 피드백 200ms.

**C-2 판정 — 밖.** 의사가 등장하지 않는다. 흡수 후에는 `/home`의 판정이 적용된다.

**옮길 때 함께 고칠 것** — 현재 `/questions/:id`의 뒤로 가기(`‹ 사연`)와 삭제 후 이동, `/news`·`/me/appointments`의 `사연 둘러보기`가 `/stories`를 가리킨다. 전부 `/home`으로 바꾼다.

**금지** — 공감 수로 줄을 세우는 것. **어느 글이 위에 오는지를 우리가 정하면 그게 곧 노출 우선권이다**(원칙 4). HOT은 별도 탭이고 **그 안에서도 최신순**이다. 진료과 필터를 늘 펼쳐 두지 않는다 — 필터가 목록보다 길어지면 사연이 밀린다.

### `/doctor/home` · 의사 홈

**구현 상태** — 있음. 잔여 답변 횟수(D-8)가 여기에도 필요하다 — 미구현.

**누구의 무엇을 해결하나** — P2. *「진료 사이 빈 시간, 점심, 마감 후. 길게 못 본다.」* 이 화면이 답하는 질문은 하나다 — **지금 내가 해야 할 일이 있나.**

**왜 이렇게 생겼나**

- **진료 신청을 목록에 섞지 않고 맨 위에 세운다.** 사연은 비동기지만 **진료 신청은 저쪽에서 사람이 기다리는 일**이다. 성격이 다른 것을 같은 목록에 넣으면 급한 것이 묻힌다
- **숫자 세 개를 먼저 준다.** 나를 지목한 사연 / 내 과·키워드 / 받은 예약. 길게 못 보는 사람에게 「몇 건인가」는 「무엇인가」보다 먼저 필요한 정보다
- **알림 상한을 화면에 적는다.** 알림이 쏟아지면 의사는 알림을 꺼 버리고 급한 것도 놓친다. 상한에 걸려 안 보낸 건수를 밝혀 「안 온 게 아니라 안 보낸 것」임을 알린다

| 상태 | 화면 | 다음 |
| --- | --- | --- |
| **비어 있음** | `지금은 기다리는 사연이 없어요` / `새 사연이 올라오면 알림 설정에 따라 여기에 쌓입니다.` **초기 커뮤니티에서 의사가 가장 먼저 보는 화면이다.** 「없다」로 끝내지 않고 키워드를 넓히는 길을 함께 둔다 | `/doctor/me/keywords` |
| 불러오는 중 | 숫자 세 개 자리 골격 + 목록 골격 3줄 | — |
| 정상 | 프로필·진료시간 → (있으면) 진료 신청 알림 → 숫자 3개 → 기다리는 사연 최대 5건 → 알림 상한 | 각 목록 |
| 오류 | `AppNotice` 공통형 + `다시 불러오기` | 재시도 |
| **권한 없음** | 면허 미검증: `면허 검증을 마쳐야 질문이 전달되고 답변을 쓸 수 있습니다.` **목록이 비는 것이 아니라 이유를 적는다** | — |

**동작** — 진료 신청 알림 → `/doctor/visits`. 숫자 3개 → 각 목록. 사연 줄 → `/doctor/questions/:id`. 알림 상한 줄 → `/doctor/me/keywords`.

**문구**

- 진료 신청 알림: `비대면 진료 신청 {n}건` / `환자가 진료방을 기다리고 있습니다. 눌러서 여세요.`
- 숫자 3개: `나를 지목한 사연` · `내 과·키워드` · `받은 예약`
- 알림 상한: `오늘 알림 {n} / {상한}` + `상한을 넘겨 {n}건은 알리지 않았습니다. 사연 모음에서 볼 수 있어요.` 또는 `키워드와 알림 상한을 바꾸면 여기에 오는 사연이 달라집니다.`
- **잔여 답변 횟수(신설):** `오늘 남은 답변 {n}회 · 매일 자정에 다시 채워집니다`

**제약** — 입력 칸 0개 · 목적 1개(오늘 할 일 확인) · 목록은 **5건까지만**(전체는 각 탭에 있다) · 첫 피드백 200ms.

**정렬** — 기다리는 사연: 나를 지목한 것 먼저, 그 다음 키워드로 걸린 것. 각 묶음 안에서는 **원래 순서 그대로**. 화면에 적는다.

**C-2 판정 — 밖.** 의사에게 사연을 보여 주는 방향이다. **✅ 구조**(사연 → 의사 인박스)의 첫 칸이며, 반대 방향(환자에게 의사를 고르는)은 여기 없다.

**금지** — 답변 수·평점 순위표(의사끼리 줄 세우면 그게 참여 압력이 되고, 압력이 홍보 동기와 만나면 답변이 광고가 된다) · 진료 실적·수입 지표(C-1) · 「내 답변으로 예약 n건」(C-1 — 성사 연동으로 읽힌다).

### `/doctor/inbox` · 받은 질문 — **변경 · 우선**

**구현 상태** — **변경.** 화면은 있으나 **하루 답변 상한 자체가 코드에 없다.** `grep -ri "answerLimit\|dailyAnswer" src/` → 0건.

- **초기화 시점을 함께 보여 준다.** 언제 다시 채워지는지 모르면 희소성이 아니라 그냥 막힘이다
- **상한에 닿았을 때의 문구는 차단이 아니라 완결로 쓴다** — 오늘 할 일을 끝냈다는 쪽

| `화상 진료방 열기` | `status → in-progress` + 진료방으로 | 있음 |
| `진료 마침` | `status → completed`. 목록에서 빠지고 환자 홈에서도 내려간다 | **미구현** |
| `이번엔 어렵습니다` | `status → declined`. ⚠︎ 되돌릴 수 없다. 확인 한 번 | **미구현** |
| `사연 먼저 읽기` | `/doctor/questions/:id` | 있음 |

**거절 문구는 이미 쓰여 있으나 도달할 수 없다** (`encounterTrack.ts:41-48`): `이번 신청은 받지 못했습니다` / `{의사}이 비대면으로 보기 어렵다고 판단했습니다. 대면 진료를 예약하거나 다른 의사에게 물어볼 수 있습니다.` — **네 동작을 만들면 살아난다.**

**문구** — 상태 칩 `신청 도착` / `진행 중` · 예약 칩 `확정 전` · 하단 `시연용 화면입니다. 예약 확정은 병원이 하며 이 화면에서 이루어지지 않습니다.`

**제약** — 입력 칸 0개 · 목적 2개(신청 처리 · 예약 확인) · 첫 피드백 200ms.

**정렬** — 신청은 도착순. 예약은 희망 날짜순. 화면에 적는다.

**C-2 판정 — 밖.** 이미 나를 고른 환자의 요청이다.

**금지** — 신청 수락률·응답 속도 지표(경쟁 지표가 되고 그게 곧 순위가 된다) · 진료비·수납 화면(D-4) · 환자에게 다른 의사를 제안하는 경로(C-2).

> ⚠️ **`받은 예약 요청` 카드의 `화상 진료방 열기`는 예약 id를 방 주소로 쓴다**(`DoctorVisitsScreen.tsx:144`). 대면 예약에 화상 진료방을 여는 것은 흐름상 맞지 않는다 — 정리 대상.
> ⚠️ **`진료방 바로 열기`(`demo-{doctorId}`)는 시연 장치다.** 주소를 아는 사람은 누구나 들어온다. 실서비스 제거 대상.

### `/doctor/visit/:roomId` · 화상 진료방 (의사)

**구현 상태** — 있음. 환자 쪽과 **같은 컴포넌트**(`ConsultScreen`, `role="doctor"`)다.

**누구의 무엇을 해결하나** — P2. 실패는 「통화하면서 기록까지 손으로 쓰는 것」이다. 길게 못 보는 사람에게 통화 후 정리 시간이 통화만큼 걸리면 다음부터 안 한다.

**왜 이렇게 생겼나** — **한 컴포넌트에 역할만 다르게 넘긴다.** 두 벌로 만들면 동의 절차·마이크 종료·자격 판정이 한쪽만 고쳐지고, 그 어긋남이 「의사 쪽에서만 마이크가 안 닫히는」 종류의 사고가 된다. **역할로 갈리는 것은 보이는 것뿐이고 안전 장치는 공유한다.**

**다섯 상태** — `/visit/:roomId`의 표를 그대로 따른다(비어 있음 · 불러오는 중 · 정상 · 오류 · 권한 없음). **권한 없음도 같다** — 담당 의사가 아니면 서버가 그 방을 내 `encounters`에 주지 않는다.

**환자 쪽과 다른 것은 셋뿐이다.**

| 차이 | 내용 |
| --- | --- |
| 키워드·기록 초안 | **의사에게만 보인다.** 환자 화면에 띄우면 진단으로 읽힌다(C-5) |
| 통화 중 응급 신호 | `통화 중 응급 신호가 나왔습니다` + 사유별 안내. `role="alert"` |
| 기다리는 문구 | `환자를 기다리는 중` (환자 쪽은 `의사를 기다리는 중`) |

**제약** — 입력 칸 1개(손으로 넣는 줄) · 목적 1개(통화) · 셸 숨김 · 기록 초안 복사는 **한 번 누르면 끝**이어야 한다.

**정렬** — 통화 기록은 시간순, 키워드는 나온 순서. 정렬하지 않는다.

**C-2 판정** — 해당 없음. 당사자 둘만 있는 방이다.

**금지** — 뽑힌 키워드를 진단으로 쓰는 것. 기록 초안에 진단·처방을 자동으로 넣는 것(C-4 — 작성 주체는 의료인이다). 통화 내용을 서버에 저장하는 것(화면에 저장하지 않는다고 적혀 있다 — 원칙 6).

### `/doctor/me/profile` · 프로필 설정 — **변경 (C-3)**

**구현 상태** — 있음. **읽기 전용**이며 값이 픽스처 고정이다. C-3 축소가 미구현.

| --- | --- |
| 비어 있음 | 값이 없으면 `아직 적지 않았습니다.` — C-3 축소 후 자기소개·약력이 사라지면 **섹션째 없앤다** |
| 불러오는 중 | 해당 없음 |

| 오류 | 해당 없음(읽기 전용) |

### `/doctor/me/keywords` · 키워드 및 알림

**구현 상태** — 있음

**누구의 무엇을 해결하나** — P2. *「내 과·내 키워드에 걸린 것만 본다」*의 설정 자리다. 그물이 너무 좁으면 사연이 안 오고, 너무 넓으면 알림이 쏟아져 알림 자체를 꺼 버린다.

**왜 이렇게 생겼나**

- **키워드는 의사가 직접 정한다. 노출 우선권을 사는 수단이 아니다.** 매칭에만 쓰이고 정렬을 바꾸지 않는다 — 화면에 그렇게 적는다
- **입력을 「진료 보고 싶은 사례」로 묻는다.** 「키워드를 입력하세요」로 물으면 SEO처럼 쓰게 된다. 무엇을 보고 싶은지로 물으면 진료의 언어로 답한다
- **알림 상한을 고르게 한다.** 상한을 넘긴 것은 버리지 않고 몇 건이 남았는지만 알린다

| 상태 | 화면 |
| --- | --- |
| **비어 있음** | 키워드 0개. 미리보기 칩 자리가 비고 `아직 등록한 키워드가 없습니다. 내 진료과로 분류된 사연은 키워드 없이도 옵니다.` — **없어도 굶지 않는다는 사실을 적는다** |
| 불러오는 중 | 해당 없음 — 로컬 설정 |
| 정상 | 입력 + 미리보기 칩 + 알림 상한 6단계 + 저장 |
| 오류 | 저장 실패: `AppNotice` 공통형. 입력은 남는다 |
| 권한 없음 | 해당 없음 |

**동작** — 쉼표·줄바꿈으로 나눠 입력 → 미리보기 칩 즉시 갱신 · 알림 상한 `3 5 10 15 20 30` 중 하나 · `저장`.

**문구** — `진료 보고 싶은 사례` · `어떤 환자를 보고 싶은지 적어 주세요. 여기 적은 말이 들어간 사연이 사연 모음에 올라옵니다. 쉼표나 줄바꿈으로 나눕니다.` · 예시 `예) 만성 비염, 축농증, 오래가는 코막힘` · 상한 `이 수를 넘기면 알림을 보내지 않습니다. 남은 사연은 사연 모음에서 볼 수 있습니다.` · 하단 `키워드는 노출 우선권이 아닙니다. 매칭에만 쓰이고 정렬을 바꾸지 않습니다.`

**제약** — 입력 칸 2개(키워드 · 상한) · 목적 1개 · 첫 피드백 즉시(칩 미리보기).

**정렬** — 미리보기 칩은 입력 순서. 정렬하지 않는다.

**C-2 판정 — 밖, 그리고 이 화면이 ✅ 구조의 근거다.** 키워드 매칭은 **사연 → 의사 인박스** 방향으로만 흐른다. 반대 방향(환자에게 의사를 골라 주는)은 만들지 않는다. `matchDoctors`가 과금·광고 인자를 아예 받지 않도록 만든 것이 그 구조적 보증이다.

**금지** — 키워드 수를 돈으로 늘리는 것(C-1) · 인기 키워드 추천(플랫폼이 매칭에 개입하는 것이 된다) · 환자 화면에서 의사 키워드를 보는 것(그 순간 키워드가 광고 문구가 된다).

### `/doctor/me/telemedicine` · 비대면 진료 설정

**구현 상태** — 있음

**누구의 무엇을 해결하나** — P2. 내가 받을 수 있는 것과 없는 것을 미리 정해 둔다. 안 정해 두면 못 받을 신청이 들어오고, 거절이 쌓이면 환자 쪽 실패(「이번 신청은 받지 못했습니다」)가 는다.

**왜 이렇게 생겼나** — **의료기관 설정이 위에 있다는 것을 적는다.** 의사가 켜도 의료기관이 비대면을 운영하지 않으면 신청이 열리지 않는다. 그 사실을 안 적으면 「켰는데 왜 안 되지」가 된다.

| 상태 | 화면 |
| --- | --- |
| 비어 있음 | 시간대 0개 선택: `비대면을 여는 시간대를 하나도 고르지 않았습니다. 이대로면 신청이 들어오지 않습니다.` |
| 불러오는 중 | 해당 없음 |
| 정상 | 운영 토글 2개 → 한 건 시간 → 시간대 → 환자에게 보이는 안내 |
| 오류 | 저장 실패: `AppNotice` 공통형 |
| 권한 없음 | 의료기관이 비대면 미운영이면 토글은 켜지되 효과가 없다. **그 사실을 하단에 적는다** |

**동작** — 토글 즉시 저장(폼 제출이 없다. 스위치는 누른 것이 곧 결정이다) · 한 건 시간 `10 15 20 30`분 · 시간대 `새벽 오전 오후 야간` 다중 선택.

**문구** — `끄면 환자 프로필에서 신청 버튼이 비활성으로 남습니다` · `재진만 받으려면 꺼 두세요. 초진은 같은 지역만 가능합니다` · 하단 `{의료기관명}의 비대면 운영 여부와 월 비율 상한은 의료기관 설정에서 옵니다. 여기서 켜도 의료기관이 운영하지 않으면 신청이 열리지 않습니다.`

**제약** — 입력 칸 4종(토글 2 · 시간 1 · 시간대 다중) · 목적 1개.
**정렬** — 시간대는 새벽→오전→오후→야간 고정.
**C-2 판정** — 해당 없음.
**금지** — 「비대면을 켜면 더 많은 환자를 만납니다」류의 유도(C-2 — 우리가 켜라고 권하는 순간 우리가 진료 성사에 관여한 것이 된다) · 시간대별 노출 우선권(C-1).

> ⚠️ `설정 확인 완료` 버튼은 **아무것도 저장하지 않고 스크롤만 올린다.** 저장은 토글 즉시 일어난다. 저장 버튼처럼 보이는 것이 저장하지 않으면 안 눌린 줄 알고 다시 누른다 — 문구를 `맨 위로`로 바꾸거나 없앤다.
